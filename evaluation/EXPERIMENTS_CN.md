## 1. 问题是什么，怎么度量

### 1.1 行为生物特征认证与 HMOG

手机在你不输密码时靠「你怎么用手机」持续判断是不是机主，这叫**行为生物特征认证**（behavioural biometric authentication）。可用信号两类：**触摸轨迹**——手指按下到抬起之间那串 (x, y, 时间戳) 采样点，反映习惯落点与划动速度曲线；**惯性传感器**（IMU，Inertial Measurement Unit，即加速度计 + 陀螺仪）——点屏幕时手机在手里的微小晃动，反映握持姿势与手腕支撑方式。

本文实验全部建在 **HMOG** 上：一个公开的手机行为生物特征数据集，同时记录触摸事件与惯性读数，是少数能同时评测两个通道的语料。连续会话被切成**动作**级片段，共五种：**tap**（点击）、**scroll**（滚动）、**swipe**（滑动）、**pinch**（捏合）、**keystroke**（按键）。

### 1.2 攻击目标、「五-shot」威胁模型与术语约定

我们做的是**攻击方**：合成假的行为数据，让部署好的检测器把它当成真人数据接受；成功与否只看检测器是否放行。

威胁模型是**五-shot 条件**（five-shot）：攻击者只拿到目标受害者的**五条真实样本**，此外没有该用户任何数据。五是发布版的配置（代码里的**参考条数** `k_refs = 5`），对应现实可达的能力——肩窥或一次短暂借用手机就能录到的量。消融把 `k_refs` 扫到 0/1/3/8。

**术语约定（全文只用这一套叫法）。** 下文把本文方法的最终定稿产物统称**发布版（release）**——它既是被评测的攻击方法，也是消融表里的 A1 基准（表里首次出现时写「A1（= 发布版）」），还是所有基线共用的载体数据来源；不再出现「本文方法」「release」等别称。威胁模型一律写「五-shot 条件」，参数一律写「参考条数 `k_refs`」，不写「参考条件数」。一个方法不建模某个动作时记为 **declined（拒绝报数）**，不写「拒答」。

**这个威胁模型对基线是双向不公平的，必须和结果一起说。** 每个 build 的 `release.json:baseline_threat_model` 逐份记着两边的训练数据：基线是 "every genuine event of the 70 train-split users, pooled across users; the generator is user-agnostic"，发布版是 "five real events of the victim, per user, per action"；该字段自带读法（`reading`）——"the baselines see far more data than the source method and are not conditioned on a victim; a baseline that still loses is losing on generation quality, and one that wins may be winning on data volume"。即：基线看到的数据多得多，但它不针对任何受害者；发布版数据少得多，但它是受害者条件化的。**所以「发布版 IMU 0.835 对 ImagenTime 0.683」这 0.152 不能整份记在生成质量上。** 同条件的比较点是消融臂 A2（`k_refs = 0`，同样不看受害者）：把三方都放到 A2 覆盖的那 24 个 IMU 格子上（A2 拒绝 keystroke，故排除该动作）重算，发布版 0.835、A2 **0.779**、ImagenTime **0.720**——受害者条件本身值 0.056，剩下的 0.059 才是在「都不看受害者」的条件下比出来的。

### 1.3 数据与评测协议

HMOG 共 **100 位用户**，按固定随机种子切成**用户不相交**的 70 / 10 / 20（`data/splits/users_seed42.json`；数据集侧记作 `split_policy: fixed_user_disjoint_70_10_20`，五个动作共用同一份划分）：70 人的真人事件用于训练生成器，10 人用于调生成器与选检查点，20 人保留给最终评测。四个学习型基线的生成器同样只训在这 70 人上（见 1.2；pyclick 与 ghost-cursor 不含学习成分，不训练）。

**受害者是全部 100 位用户**：伪造事件按用户逐份生成，每位受害者的五条参考取自他自己的真实事件，并从真人事件池里**剔除**（`selected_genuine_touch_source_exclusion: true`，实测与所选真人事件重叠 0 条）。发布版数据集共 145,776 条事件 = 100,000 条伪造 + 45,776 条真人，每个动作 20,000 条伪造。

检测器**不是**「本人 vs 他人」的身份核验器，而是**每格一个「真人 vs 伪造」二分类器**（`schema_version: formal_event_pad_action_cell_v5`，即伪造检测 / PAD）：全局一个，不按受害者分，因此这套协议里**没有注册（enrollment）阶段**，也不存在「用某个受害者的几条数据建模板」这一步。检测器的训练 / 开发 / 评测三份数据沿用同一条用户不相交划分，每个动作分别是 14,000 / 2,000 / 4,000 条伪造事件；真人一侧以 scroll 为例是 7,000 / 1,000 / 2,000 条，逐动作数值见 2.1。阈值在**开发集**（10 人）上选定并冻结，只在**评测集**（20 人）上用一次。

评测的最小单位叫**格子（cell）**，即「动作 × 模态 × 检测器」一个三元组，一格出一个数（为什么要铺满，见 1.6；模态指检测器读哪些通道，见 1.7）。「**载体（carrier）**」指被替换通道所在的那条伪造事件的其余全部内容——行数、时钟列、真人行等等（详见 2.1）。

### 1.4 两个操作点：主判据 FRR=5% 上的 FAR，对照判据 test 上的 EER

检测器要选一个**判决阈值**，两种常见选法：**EER**（Equal Error Rate，等错误率）把阈值挪到「拒真率 = 假接受率」那一点；**FRR = 5%**（False Rejection Rate，拒真率）先规定「最多误拒 5% 的真人事件」，再倒推阈值。

**部署时用的是后者**：厂商先定用户能忍受的误拒比例，再看这个前提下漏进来多少假货。发布版这 90 格上逐格重算，EER 阈值平均要拒掉 **33.6%** 的真人事件（`summarise_far5.py`（内部脚本，未发布）文件头写的「约 37%」是早期网格上的值），没有产品会这样发货；FRR=5% 阈值上实测拒真率均值 5.2%、最高 9.6%。所以判据统一为：

> **FAR**（False Acceptance Rate，假接受率）**= 在开发集上选定的 FRR=5% 阈值处，被检测器接受的伪造样本比例。FAR 越高，攻击越强。** 成功线定在 FAR ≥ 0.60。

**0.60 是本项目自定的工程判据，不是文献标准**：取「过半伪造尝试被放行」作为「攻击已经实用」的分界，没有更强的出处。正因为它是约定，所有表格都同时给出均值与中位，「≥ 阈值的格子数」这一列读者可以换任何一条线自行重算。

口径必须锁死，因为**同一批分数存在三个不同的操作点，数值差得很远**：

| 操作点 | 阈值怎么定 | 发布版 90 格 |
|---|---|---|
| **① FAR @ FRR=5%**（本文主判据） | 开发集上定，冻结后才碰评测集 | 均值 **0.775**、中位 0.794 |
| ② FAR @ EER 阈值 | 开发集上定等错误点，评测集上量 FAR | 均值 0.386、中位 0.391 |
| ③ **test EER**（文献常用，见下） | **在评测集上**把阈值挪到等错误点 | 均值 **0.361**、中位 0.369 |

每个格子产物默认写出的 `far` 字段是 **②**（例如 `keystroke__imu_only__authconformer` 的 `summary.json` 记 0.4725，同格切在 `frr5` 上是 0.914），直接汇总会系统性低估攻击面。取数一律走 `summarise_final.collect(method, metric)`，`metric` 只接受 `far5` 与 `test_eer` 两个值。

主判据的阈值一律在**开发集**上选、评测集上用，不允许看过攻击样本后再挑；每格 `summary.json` 里的 `test_threshold_selection_calls: 0` 就是这条纪律的机器记录。

**为什么还要报 test EER。** 行为生物识别文献里多数报 EER，且多数是在评测集上定位那个等错误点。为了可比，同一批 438 格在这个操作点上也全部算了一遍，结果单独成表（`RESULTS_EER.md`，由 `eer_tables.py` 生成）。**这是较弱的协议**——等错误点是看着评测集的分数挪出来的。发布版自己的产物把同一个量记作 `primary_metrics.descriptive_test_eer`，`descriptive`（描述性）这个词正是在标注这一点；`eer_tables.py --check` 把 438 格的重算值与各格自记的该字段逐一比对，当前 0 处不一致。

**两张表怎么一起读：排序不变，尺度大变。**

| | FAR @ FRR=5% | test EER |
|---|---|---|
| 发布版（IMU，30 格） | 0.835 | 0.397 |
| ImagenTime（IMU，30 格） | 0.683 | 0.301 |
| TTS-GAN（IMU，30 格） | 0.124 | 0.063 |
| *真人对照（IMU，30 格）* | *0.773* | *0.447* |

方法之间的名次两表完全一致（消融臂也一样，见第 5 节）。变的是绝对水平，原因是**两个量的上界不同**：FAR 的上界是 1.0，EER 的上界是 0.5（真假完全分不开时两类错误各占一半）。所以 0.397 不该读成「只有四成」——**真人对照的 0.447 才是这条流水线上可达的天花板**，发布版到了它的 **89%**，ImagenTime 到 **67%**。

由此有一条硬规定：**「≥0.60 的格子数」这一列只属于主判据**。FRR=5% 口径下 77/90 格过线，EER 口径下 0/90 格过线——这是尺度差异，不是结论翻转。把 0.60 这条线搬到 EER 表上会得出「没有任何攻击成功」的错误印象。

（一个边角观察：EER 最大的一格是 0.536，**超过了 0.5**。这不是计算错误——它意味着该格检测器的分数与真值轻微反相关，比随机猜还差一点。个别格子出现这种情况在预期之内，不影响均值层面的结论。）

发布版在此判据下的总成绩：90 格**全部跑出了结果**，**均值 FAR 0.775、中位 0.794，77/90 格 ≥ 0.60**。

**这些检测器不是形同虚设，EER 高是「被发布版考」这一格的性质。** 同一套检测器、同一条阈值规则去考最弱的攻击 TTS-GAN：EER 阈值只拒掉 5.7% 的真人事件，FRR=5% 上的 FAR 是 0.124、中位 0.008——平均挡下 87.6% 的伪造事件，一半格子挡下 99% 以上。刻度的另一端由 Control 给出（把**真人**惯性窗口当作「伪造」通道灌进同一条流水线）：30 格均值 0.773。发布版的 IMU 0.835 应当放在 0.124–0.773 这条刻度上读。**明确未测量**的是「零努力冒充者」（拿另一个真人当冒充者）在同一操作点上的 FAR：本文的检测器不做身份核验，当前口径下没有对应的实验，第 7 节把它列为影响结论解释力的限定。

### 1.5 六个检测器：三类范式各两个

| 检测器 | 类型 | 特征来源 |
|---|---|---|
| `hmog_style_svm` | 线性 SVM（`LinearSVC`） | HMOG 风格统计特征 |
| `hmog_style_rf` | 随机森林 | HMOG 风格统计特征 |
| `paper_svm` | 线性 SVM | RiskCog 式运动统计 + Touchalytics 式触摸特征 |
| `paper_xgboost` | XGBoost 梯度提升树 | 同上 |
| `behaveformer_stdat` | 深度序列模型（BehaveFormer STDAT，时空双注意力） | 直接吃原始序列 |
| `authconformer` | 深度序列模型（AuthConFormer，卷积 + 注意力） | 直接吃原始序列 |

两个 HMOG 风格检测器是对 HMOG 统计式方法的改编，非精确复现。覆盖「**传统特征工程 + 树模型 + 深度序列模型**」三类，因为它们看的东西不同：SVM 看特征空间里的线性可分性；树模型对**单个统计量的取值区间**极其敏感；深度模型看波形的时序结构。树模型这一条本项目付过学费：某个构建把 `elapsed` 时钟列写成精确十进制，而真人数据的同一列经过一次 float32 往返，于是伪造事件的时间列 100% 与理想等间隔斜坡逐位相同、真人只有 4.76%；只喂 `elapsed_s.skew` 这一个特征，FAR 就从 0.847 掉到 0.000，`paper_xgboost` 的联合模态格子从 0.339 掉到 0.009，而两个 SVM 与两个深度模型的分数几乎不动——轴对齐的树能一刀切在这种量化残差上，另两类画不出这么锐的边界。只骗过其中一类不算数。发布版在 IMU 模态上逐检测器均值从 `paper_xgboost` 的 0.774 到 `behaveformer_stdat` 的 0.868，跨度 0.09。

### 1.6 为什么是 90 格

5 动作 × 3 模态 × 6 检测器 = **90 格**为完整网格（格子的定义见 1.3）。

铺这么大是因为**单个检测器上的成功极可能只是过拟合了那个检测器**。例证：第 4 节的消融臂 A7（消融的每个变体称为一个**臂 / arm**，即同一方法被评测的一个变体配置）只重训了 scroll 与 swipe 两个动作，**所以下面这组数字一律限定在这两个动作、IMU 模态的同一批 12 格上**（发布版在四动作 24 格上的对应值是另一个口径，与 A7 不可相减，见 §4.7）：A7 在 hmog_style_svm 上 0.901，比发布版同 12 格的 0.859 还高，看这一列会以为它没退化；同一臂在 hmog_style_rf 上只有 0.581，发布版同 12 格是 0.772。只报一个检测器，结论会完全反过来。动作维度同理：发布版轨迹模态上 tap 0.901，scroll 只有 0.685。

### 1.7 三个模态，以及「只在改动过的模态上评测」

模态指检测器**读哪些通道**：`trajectory_xytime`（轨迹）只读触摸的 x、y 和时间列；`imu_only`（IMU）只读加速度计与陀螺仪；`imu_trajectory_xytime`（联合）两者都读，是最难骗的一档——发布版在联合上均值 0.711、21/30 格过线，低于单通道的 0.777（轨迹）与 0.835（IMU）。

一条纪律必须写死：**一个方法只在它真正改动过的模态上被评测**。评测时假数据是「换进载体」的：某方法只生成 IMU，其轨迹列继承自载体，而载体的轨迹列装的是**发布版自己的伪造轨迹**。把纯 IMU 方法拿去跑轨迹格子，跑的其实是我们的数据，分数被拉向发布版——等于把自家成绩挂在别人名下。同理，单通道方法的**联合模态**格子也排除——那里一半通道是发布版的。项目已因此**删掉 48 个白跑的格子**，驱动遇到没碰过的模态直接报错退出并永久剔除；依据是 `release.json` 的 `baseline_swapped` 字段（`covered_modalities.py` 读取），不靠人记账。

**动作**维度同理：方法若不建模某动作（pyclick 与 ghost-cursor 都不生成 keystroke），就记为 **declined（拒绝报数）**，那些格子不进汇总——这两个基线的分母因此是 24 格而非 30 格。declined 格子里躺的仍是载体的假信号即发布版的产物，算进去等于替对手虚报。

## 2. 实验台怎么保证公平

### 2.1 原位替换（in-place swap）：唯一变量是那一条通道

**原位**＝写回原伪造事件的**同一批行**：行数、起止偏移、用户 ID、会话 ID、事件 ID、划分、
样本序号全不动（此处与 1.4 节的「评测格子」无关，那是另一个词）。所有方法都不自己造数据集，
它们只提供**一条通道**（触摸坐标，或六轴惯性波形），由实验台把它写回发布版数据集里对应的
那一条伪造事件。这里的「载体（carrier）」指那条伪造事件原有的全部内容：采样更新时序、
**无接触哨兵值**（手指未接触屏幕的行携带精确的 `(0, 0)` 坐标，keystroke 约 80% 的行是这种行）、
时钟列（`elapsed`），以及全部**真人事件**。这些一律**保持逐字节相同**。数据集按用户存盘，
**每个用户一份压缩分片（shard）**，发布版每个 bundle 共 100 个分片；分片里的坐标是相对屏幕
归一化到 [0,1] 的（3.5 节把像素坐标「换算回分片的归一化坐标」就是换算到这个尺度）。
`verify_harness.py` 逐分片核对上述不变量。于是两个方法之间唯一的差别，就是被替换的那条通道。

具体到九列：一次轨迹替换只允许动第 1、2 列（x、y）；第 5、6 列（dx、dy，逐步位移）**不是
自由参数**，`recompute_deltas` 会从新写进去的 x、y **确定性重算**它们——保留源的 dx/dy 会让
这两列描述一条并不存在的路径；第 0、3、4、7、8 列（接触标志、压力、指针数、时钟 `elapsed`、
可用性）必须与源**逐位相等**，`verify_harness.py` 里的 `UNCLAIMED_TRAJECTORY_COLUMNS`
就是这五列。一次 IMU 替换替掉全部六个惯性通道，不许碰九列轨迹中的任何一列，反之亦然。

**bundle**：一次完整的数据集构建产物。发布版的五个动作不是一次构建出来的，而是分四次定稿，
得到四个 bundle——`tap_and_pinch`、`scroll`、`swipe`、`keystroke`。每个 bundle 里都躺着五个
动作的伪造事件（各 20,000 条，合计 100,000 条），但只有它**「拥有」**的那一个（或两个）动作
参与打分，其余动作的行原样保留发布版自己的伪造信号，不算数。所以一个方法要建四份：
`tap_and_pinch` 拥有 tap 与 pinch 两个动作 → 2 × 3 模态 × 6 检测器 = 36 格，其余三个 bundle
各拥有 1 个动作 → 各 1 × 3 × 6 = 18 格，合计 18 + 18 + 18 + 36 = **90 格**。这也是 4.7 节里
A7 只能把 tap 和 pinch 一起做或一起不做的原因：它们同属一个 bundle，重训是按 bundle 走的。
打分只用评测划分，每格 4,000 条伪造事件，真人事件按动作为 tap 1,042、keystroke 1,950、
pinch 1,999、scroll 2,000、swipe 2,000。

**数据规模、划分与攻击者预算。** 每个 bundle 都是 145,776 条事件 = 100,000 条伪造 +
45,776 条真人，来自 100 个用户，按 `fixed_user_disjoint_70_10_20` 做**用户不相交**的三划分
（70 训练 / 10 开发 / 20 测试用户，同一个人不会同时出现在两个划分里）。逐动作计数
（`release.json:action_label_counts`）：训练 14,000 假 + 真人 tap 4,306 / scroll 7,000 /
swipe 6,959 / pinch 6,945 / keystroke 6,976；开发 2,000 假 + 真人 tap 601 / scroll 1,000 /
swipe 1,000 / pinch 998 / keystroke 1,000；测试 4,000 假 + 真人 tap 1,042 / scroll 2,000 /
swipe 2,000 / pinch 1,999 / keystroke 1,950。每一格的检测器就在对应动作的这套训练集上**从零
训起**、在开发集上切阈值、在测试集上出分。伪造事件覆盖全部 100 个用户（消融缓存里正是
`user_000`–`user_099` 一百个目录），但每格的测试分只落在 20 个测试用户身上。
两边拿到的数据量并不对称，`release.json:baseline_threat_model` 把这件事写死了：第三方生成器
训练用的是**70 个训练划分用户的全部真人事件**、跨用户混池、不针对任何受害者；本文方法拿到的是
**受害者本人的五条真实事件，逐用户、逐动作**——五个动作合起来是 5 × 5 = **25 条**
（1.2 节说的「五条」指每个动作五条，不是总共五条，攻击者的真实取样成本要按 25 条算）。
所以基线看到的数据远多于本文方法：一个基线仍然输，是输在生成质量上；赢了则可能赢在数据量上。

### 2.2 替换规则被逐位验证过：80,000/80,000

替换规则本身可能出偏差：如果它把 A 事件的波形写进了 B 事件的行，或者重采样时多做了一次
平滑，那么所有对比都无效——数据集照样能训练、照样给出一个看着合理的 FAR，错误完全不可见。
所以这条规则用**发布版自己**验证：拿发布版的**生成缓存**（发布版当初逐事件采样出来、composition
时写进数据集的那批原始波形，按 `sample_idx` 可寻址），按同一条规则重建它的 IMU 通道，
要求与已发布数值**逐位相等**（不是接近、不是相关）。实测 `verify_reconstruction.py`：
scroll、swipe、pinch、tap 各 20,000/20,000，合计 **80,000/80,000 完全一致，0 条缺失**。
keystroke 不在这个分母里，理由是构造性的：发布版的 keystroke 伪造 IMU 由**解析适配器**写出
（`diffusion_used: false`，生成器源是 `security_exp/keystroke_imu_pulse.py`），它根本没有可
重放的扩散生成缓存去比对，所以重建证明只能覆盖四个动作、80,000 条——同一条构造事实也是 2.5
节里消融臂拒绝 keystroke 的理由。

`verify_harness.py` 另有四项配套检查：**[1] 路由**（生成器写入一个由事件 ID 派生的指纹，
必须落在该事件自己的行里；「原样返回」的恒等生成器测不出这一点，所以载荷必须依赖身份）、
**[2,3] 真人行与不该动的列未被改动**、**[4] 替换确实发生**（与源完全相同的数据集会通过所有
「没变」的检查）、**[5] 载体时钟不是破绽**。

第 [4] 项有个已量化的例外：只剩 1–2 行可自由改写的事件，首行是锚点、末行是绑定目标，
任何方法都只能写出同样的坐标——发布版 tap bundle 上，ghost-cursor 对「1 行自由」的事件
100% 与载体相同，「2 行自由」75%，「≥3 行自由」0%，判据的门限取「≤2 行」就是这么定出来的。
**这个例外有多普遍，验证日志每次都直接印出来**：按「≤2 行自由」判，`scroll` 与 `keystroke`
两个 bundle 各 **18,266 / 100,000**，`swipe` 与 `tap_and_pinch` 两个 bundle 各
**18,478 / 100,000**（pyclick 的日志跑在上一版判据「由绑定终点唯一确定」上，四个 bundle 都是
**12,816 / 100,000**）。也就是说约 13–18% 的伪造事件在轨迹通道上，任何两个方法都会产出逐位
相同的坐标；这些格子对轨迹类比较**没有分辨力**，方向上是把 3.5、3.6 节里所有轨迹方法的分数
**一齐往载体（即发布版自己的轨迹）拉近**，压缩差距而不是放大差距。更有意义的口径是只统计各
bundle **自己拥有的动作**上的占比——该值目前**未测量**，上面这些数是全 100,000 条的分母。

第 [5] 项查的是载体自己的时钟。假事件的 `elapsed` 列是从载体继承的（生成器只管 xy 和六轴，
不碰第 7 列），而这一列曾经是个近乎完美的标签。实测「`elapsed` 与干净十进制斜坡
`(n-1) × 10.0 / 1000` 逐位相同」的比例：

| 载体版本 | scroll 真人 / 假 | swipe 真人 / 假 |
|---|---|---|
| `replay_dataset_v12` | 4.3% / **100.0%** | 4.6% / **100.0%** |
| `replay_dataset_v16` | 4.3% / 6.5% | 4.6% / 7.0% |
| `replay_dataset_zoh` | 4.6% / 3.5% | 4.2% / 3.2% |

在 v12 那种载体上，单一特征 `elapsed_s.skew` 的随机森林就能把真假完全分开——量到的任何数字
都是在描述载体的算术，不是攻击。`check_clock_fingerprint` 因此把「假事件命中率 > 50% 且超过
真人 3 倍」的数据集直接判 FAIL：实测 v12 被拒并打印上表那两行，v16 与 zoh 通过。
本文全部 18 个方法 × 4 个 bundle = **72 份验证日志，第 [5] 项全部 PASS**；每个方法的
`baseline_source_dataset` 也已逐个核对，全部指向 `direct100k_final/datasets/*`
（源自 `replay_dataset_v15`），没有一份建在被污染的载体上。所以「你怎么知道所有基线不是被
同一个载体时钟指纹一起拉高或拉低」这个问题，是有一道闸门在管的，不是没想过。

### 2.3 检测器怎么训：主表口径与迁移口径

「每个攻击各训一个检测器」和「用发布版出厂的检测器打所有攻击」是两个不同的问题，本文用两套
表分开报，不混着读。

- **主表**（第 3 节的第三方对比表，与第 4–5 节的消融表）：每一格都**重新训练**检测器、并在
  开发集上**重新选** FRR=5% 的阈值，测的是**这个攻击本身有多难被学出来**——防守方见过它再来判它。
- **迁移表**（第 6 节）：**不训练任何新检测器**，直接搬出发布版出厂的那 90 个已拟合检测器
  （连它们各自在开发集上选好的阈值一起）去打所有攻击。「迁移」是就**检测器**说的：这批模型是在
  发布版的产物上拟合的，现在要它们去判一个**没见过的生成器**，量的是这批检测器的**泛化 / 盲区**，
  不是攻击强度。

两套口径按攻击强度读会得到相反排名——主表里最弱的 TTS-GAN（IMU 均值 0.124）在迁移表里以
0.877 排到第五。详见第 6 节。

**主表那一行的检测器，到底是拿谁的伪造数据训的？** 是**那一行方法自己的**，不是发布版的——
这是读这张表最容易误解的一点，所以给出可核对的证据而不是只作声明。

代码层：`grid_against_final.sh`（内部调度脚本，未发布）把 `--manifest "$dataset/event_manifest.jsonl"` 传给检测器训练脚本，
而 `$dataset` 指向**该方法自己的产物目录**（`final/<方法>/<bundle>/`），分片也存在那里，
不是发布版的 `direct100k_final/`。每一格的检测器都是在这份数据集上**从零训练**的。

数据层：把 Diffusion-TS IMU 臂的一个分片（`final/diffts_imu/scroll/shards/hmog_u000.npz`，未发布）
与发布版同名分片逐元素比对——

| 数组 | 形状 | 结果 |
|---|---|---|
| `imu_flat` | (150721, 6) | **不同**，904,326 个元素中 76,734 个不同 |
| `trajectory_flat` | (150721, 9) | 逐位相同 |
| `label` / `offsets` / `sample_idx` | — | 逐位相同 |
| `event_id` / `session_id` / `user_id` / `action` | — | 逐元素相同 |

再定位到事件级，差异**恰好只落在这个 bundle 拥有的那个动作的伪造事件上**：scroll 的 200 条伪造
事件全部被替换（200/200），而该分片里 457 条真人事件**一条未动**，其余四个动作的伪造事件也
**一条未动**（它们属于别的 bundle，由别的 bundle 发布）。

所以基线那一行的训练集 = **该基线生成的伪造惯性通道 + 发布版原封不动的真人事件 + 发布版原封不动的
轨迹通道**。真人一侧所有方法共用同一批 HMOG 真实事件，这正是 2.1 节那条"唯一变量是那一条通道"
在检测器训练数据上的体现。每个 bundle 的伪造事件按 70,000 / 10,000 / 20,000 分入训练 / 开发 /
评测（五个动作各 14,000 / 2,000 / 4,000），三份用户不相交。

由此，主表的语义是**「防守方已经研究过这个攻击，它还骗得过去吗」**——对攻击方最不利的设定。
Diffusion-TS 的 0.325 意思是"一个针对它训练的检测器能轻易识破它"，发布版的 0.835 意思是
"即便检测器专门针对本方法训练过，仍有 83.5% 的伪造被放行"。两个数都没有被对方的数据污染过。

**不确定度，以及它没覆盖到哪里。** 每个格子的 `summary.json` 都带一份 bootstrap 95% 置信区间，
`replicates_requested: 10000`、`unit: "user_cluster"`（按用户聚类重抽，方法学上正是这种数据该
用的单位）。但它算的是 `primary_metrics` 里的 `far` / `frr`，而那两个取在
`development_eer_threshold`（EER 阈值）上——**唯一存在的区间恰好不在主判据上**。本文主表、
消融表、迁移表里的每一个数字都读自 `thresholds.json` 的 `frr5` 切点
（`selection_split: "development"`、`target_frr: 0.05`），而 FRR=5% 口径的 FAR **目前没有区间
估计**（`summarise_far5.py` 这条链路上没有 bootstrap）。补法是现成的：按 `frr5` 切点把同一套
user-cluster bootstrap 重跑一遍、把区间带进表。在补上之前，这里如实标注为**未测量**——表里两个
相近的均值不要当作有显著差异来读。

### 2.4 Control（对照）行：同流水线参照点，不是上界

Control 不是基线方法，它把**真人惯性窗口原封不动**当作「伪造」通道塞进同一条流水线，
其余一切照旧：如果送进去的东西根本不是生成的，检测器还能不能把它挑出来？
实测 Control 在 IMU 上 30 格**均值 0.773、中位 0.844、22 格 ≥ 0.60**。

这个数字应当这样读：**它是同一条流水线上的参照点（reference point），不是严格上界**。
Control 的真人窗口取自**另一条**真人事件，而且必须**重采样到检测器的固定窗长**才能塞进载体；
这两项失配是发布版不承担的——发布版的伪造 IMU 本来就是按载体行数生成的。所以 0.773 不表示
「合成质量最多只能做到这个份上」；它证明的是**这条流水线自身就会泄漏约 0.23 的可分性**
（未做归因实验，上面两项只是最可能的来源）。逐检测器看，泄漏集中在树模型：hmog_style_rf
只有 0.579、paper_xgboost 0.638，而 behaveformer_stdat 0.922、hmog_style_svm 0.896
几乎完全分不开；逐动作看 swipe 0.647 最低、tap 0.960 最高。

有了这个参照点，发布版的 0.835 该这样说：**在同一条流水线下，它不劣于经过同样重采样的真人
窗口**，而不是「比真人还真」。0.835 高于 0.773 之所以可能，正是因为 Control 多背了那两项额外
失配——把 0.773 叫「天花板」会立刻自相矛盾。反过来也要照实说：既然连真人窗口都只到 0.773，
**接近这个水位的格子之间的细微差别不宜过度解读**。

### 2.5 拒绝（declined）与未测量：两件不同的事，不能混为一谈

一个方法不建模某个动作时，它**不报数**（`declined`），而不是被随便填一个值或者悄悄退回发布版
的数据。实测的拒绝情况：pyclick 与 ghost-cursor 都拒绝 keystroke（两者各 24 格而非 30 格）；
消融臂 A2–A6（臂目录 `abl_noshot_adv`、`abl_fewshot_nonadv`、`abl_krefs1/3/8`；注意臂目录名
与 4.3 节的**采样协议名**不是一回事，例如 A3 的臂目录是 `abl_fewshot_nonadv` 而协议是
`fewshot`）也全部拒绝 keystroke，因为发布版的 keystroke 伪造 IMU 由解析适配器写成
（`diffusion_used: false`），扩散生成器的任何消融都够不到它——这是**构造上够不着**，再多算力
也变不出来，所以是 24 格。（术语：**建库**＝把采样出的窗口装配成可打分的样本库；**排格子**＝
在该样本库上逐格从零训练检测器、在开发集上切阈值、再算测试集 FAR。）

A7–A10（`abl_a7_weighted_sum`、`abl_a8_no_feature`、`abl_a9_no_set`、`abl_a10_no_waveform`）
必须重训生成器，**受算力所限只重训了 scroll 与 swipe**：A7–A10 每臂 12 格。它们的 tap 与 pinch 在建库时确实带上了 `declined` 这个标签——
但那只是建库脚本的机器标签：脚本只有「拥有 / 不拥有」一个开关，`declined = 全部动作 − 本次声明
拥有的动作`，它表达的是**这次没建**，并不区分原因。按本文自己的分类，**A7–A10 的 tap/pinch
属于「未测量（算力预算）」**，与 keystroke 的「构造上够不着」语义不同：前者补算力就能补上，
后者补算力也补不出来。tap 与 pinch 只能一起缺，是因为它们同属 `tap_and_pinch` 这一个 bundle，
重训按 bundle 走，要么整体做要么整体不做（详见 4.7 节）。

同一条原则也适用于模态：轨迹类方法没碰过惯性通道，它们的 `imu_only` 格子跑的其实是发布版
自己的数据，算进去会把分数往发布版拉，所以不报；单通道方法的联合模态同理（已因此删掉 48
格白跑的结果）。

其余**未测量**的缺口只剩一处：`diffts_both`（Diffusion-TS 双通道臂）只跑了联合模态的 30 格，
另外 60 格（纯轨迹与纯惯性）没有测——那两个模态由 `diffts_trajectory` 与 `diffts_imu` 两个单通道臂
各自覆盖，双臂的对应格子会与它们重复，所以没有排。
（A10 与 A11 在成稿前已补齐，各 12 格；早期快照里它们的缺格记录见 5.9 节。）

### 2.6 自检与冻结回执：发布版打自己，30 格，最大 |差| 0.0000

用发布版出厂的冻结检测器打发布版自己的数据，30 格逐格与已发布参考值比对，
**最大 |差| 为 0.0000**（`crossscore/_release_selfcheck.json`，未发布）。它证明的不是攻击强度，
而是三件工程事实：打分器读的确实是发布版那一份数据、阈值与参考值取自同一次评测、
「原位替换」的搬运没有引入任何数值漂移。发布版在主表和迁移表两栏数字相同是结构必然——
对它而言，「针对该攻击训练的检测器」就是「出厂的冻结检测器」。如果连恒等替换都对不上，
后面每一个差值都无从解释。

**测试集冻结回执。** 1.3 节说的「阈值一律在开发集上选、测试集上用，不允许看过攻击样本后再挑」，
在本项目里不是一句纪律声明，而是**逐格留痕的机器强制**。每个格子除 `summary.json` 外还写一份
`pre_test_freeze_receipt.json`，字段包括 `frozen_before_test_open: true`、
`test_signal_arrays_loaded_before_freeze: 0`、`test_source_paths_resolved_before_freeze: 0`、
`test_signal_file_stat_or_hash_calls_before_freeze: 0`、
`manifest_test_rows_ignored_before_freeze`；`summary.json` 里另有
`test_opened_before_freeze: false` 与 `test_threshold_selection_calls: 0`。阈值文件本身自带
口径（`selection_split: "development"`、`target_frr: 0.05`）。最后
`summary.json:artifact_sha256` 对 `frozen_config` / `model` / `thresholds` / `test_scores` /
`pre_test_freeze_receipt` 五个产物各存一份 sha256，构成一条哈希链：「先冻结、再开测试集」这件事
改动任何一环都会对不上。

### 3.1 Diffusion-TS（ICLR 2024，三个臂）

**是什么。** Yuan & Qiao 的 Diffusion-TS 是一个扩散模型：训练时把真实序列逐步加噪成白噪声，学会「去噪」这一步，采样时从纯噪声反向走回一条序列。它的特色是去噪网络内部把序列显式拆成「趋势 + 周期 + 残差」三块（可解释分解），因此对有明显周期结构的信号很有利。

**怎么跑的、改了什么。** 模型、趋势/周期分解、扩散调度、训练循环全部未改，超参用作者按序列长度给的那一套。**唯一的偏离是写了一个 Dataset 类把 HMOG 的窗口喂进去**，因为仓库只自带它自己那几个语料的加载器。在指向 HMOG 之前先复现了作者的 Sines 基准：判别分数（discriminative score，即训一个分类器区分真假、越接近 0 越难分）0.0108 ± 0.0061，作者论文是 0.006 ± 0.007，说明训练通路本身是对的。每个动作训 12000 步、采 4000 条、采样用 500 个反向步、训练用户 70 人。

三个臂分别只供给轨迹坐标、只供给惯性通道、两个通道都供给。

**结果。** 轨迹臂 30 格均值 0.460 / 中位 0.393 / 11 格过 0.60；IMU 臂 0.325 / 0.343 / 2 格；双通道臂的联合模态 0.266 / 0.205 / 3 格。逐动作差异极大：轨迹臂 tap 0.839、pinch 0.582，而 keystroke 只有 0.201；IMU 臂 keystroke 只有 0.047。逐检测器上，轨迹臂对两个 SVM 尚可（hmog_style_svm 0.590、paper_svm 0.599），对 authconformer 只有 0.287。

**未完成的部分要说清楚**：双通道臂只排了联合模态的 30 格，它自己的轨迹与 IMU 单模态共 **60 格未计算**（`comparison/notes/diffts_both.md` 末尾原样标注 "60 cell(s) not yet computed"）。另外，Diffusion-TS 作者代码自带 infill（条件补全）采样能力，模型现成，只需另写一个采样驱动就能得到一个「看得到受害者若干条样本」的条件臂——本轮**没有跑，未测量**（项目笔记 `RESUME_BASELINES_CN.md` §6 待办第 4 条；该笔记未发布）。它和 §3.2 里那个同样没跑成的 CSDI 条件臂，一起构成本文的一处已知空白：**没有任何第三方基线被给到与本方法相同的受害者条件信息**，因此第 3 节的比较始终带着「本方法有五条受害者样本、基线没有」这个不对称（各方法 `release.json` 的 `baseline_threat_model` 字段对此有原样记录：基线看到的训练数据其实远多于本方法，但不是受害者本人的）。

### 3.2 CSDI（NeurIPS 2021）

**是什么。** Tashiro 等人的 CSDI 原本不是生成器而是**插补器**：给一段有缺失的多变量序列，用条件扩散把缺失位置补上。它在医疗时序上是标准基线。

**怎么跑的、改了什么。** `CSDI_Physio` 与其去噪网络未改，损失、优化器、MultiStepLR 调度、以及 `config/base.yaml` 里的每一个超参都照用（记录在案的模型规模因此只有 413,601 个参数，扩散步数 50，训 200 epoch）。四处偏离，都写进了 README：

1. 写了一个只返回 `process_data` 真正会读的四个 key 的 Dataset（仓库只带三个医疗语料的加载器）；
2. **逐通道 z-score 归一化，这是必须而非可选**——模型内部没有任何归一化层，而作者三个官方数据集都在 DataLoader 之前标准化过；HMOG 的加速度与陀螺量级相差约 7 倍，不做就等于喂给它一个它从未见过的尺度；
3. **无条件采样**：CSDI 没有「生成」入口，把条件掩码全置 0，作者自己的 `impute` 就退化成一个普通 DDPM（denoising diffusion probabilistic model，标准去噪扩散模型），覆盖整个窗口。模型一行没动；
4. 每个 epoch 存检查点——作者的 `train()` 只在最后一个 epoch 写一次盘，而且它算了最优验证损失却从不用来存盘，一旦中断什么都不剩。

两个静默陷阱也记在 README 里：`linear_attention_transformer` 用 pip 装真包，而不是拿一个空模块替身（stub）去骗过 import，`diff_models.py` 因此与作者文件逐字节一致；`target_strategy` 保持 `random`，因为在全观测窗口上作者的历史掩码分支会让训练损失恒等于 0（训 200 epoch 什么都没学到，且不报错）。

**「五-shot 条件臂」的真实状态要如实说**（这是读者最会追问的一项，因为它是唯一一个能「同样看到受害者五条样本」的第三方对照）。这个臂**没有跑完，也从来没有进过检测器格子**：

- `csdi_queue.log`（内部调度日志，未发布）里 conditional 在 08-06 23:35 至 08-07 06:36 之间连续 4 次 `ERROR ... rerun this script to resume`（tap / swipe / scroll / pinch）；
- 重跑后只有 tap（08-07 15:42 done）和 pinch（08-07 20:49 done）出了样本，**scroll / swipe / keystroke 的 conditional 至今没有采样文件**；
- 因此它没有样本库、没有 bundle、**没有任何一个检测器格子**；`STATUS.md`（内部状态文件，未发布；最近一次刷新 08-09 10:55）仍在打印 `pipeline: csdi_fiveshot has 2/5 actions ( tap pinch) -- waiting for the rest`，即流水线仍把它挂在队列里等其余三个动作。

后来 `run_csdi_all.sh` 把默认模式收成只跑 unconditional（`CSDI_MODES` 可以把它放回来），脚本注释写的理由是「它和无条件臂共用同一个训练好的模型，只是采样时告诉采样器的掩码不同，为此多付十个检测器格子（约三小时）去添一行表格不划算」。**这句话是设计上的取舍理由，不是实测结论**——不能写成「测完之后为省开销砍掉」，因为它根本没测到格子层。这属于**未测量**而非**已测后舍弃**，与 §2.5 区分的两类缺口里的前一类同属一档，故在此照实登记。

顺带记一处**已经改掉**的产物文字：自动生成的 `comparison/notes/csdi_unconditional.md` 原先写的是 "The five-shot arm was dropped **after measurement**"，与上面的日志证据不符。成稿前已把 `comparison/code/write_baseline_readmes.py` 里这句硬编码文字改成「从未跑完，因此哪里都没测过」并重新生成，现在该说明写的是 "The five-shot conditional arm was never completed, so it is not measured anywhere"。但要注意：这一句本来就是脚本里硬编码的、不是从产物读出来的，所以 §7.7 那句「说明由产物生成、因此不会与实际跑的东西漂移」对它**依然不成立**——它靠人工维护。

**结果。** 30 格，均值 0.292、中位 0.175、4 格过 0.60。中位远低于均值说明分布极偏：tap 0.628 撑起了大部分，scroll 只有 0.108、keystroke 0.091。

### 3.3 ImagenTime（NeurIPS 2024）——唯一进入同一量级的第三方方法

**是什么。** Naiman 等人的做法是把一维时间序列用**延迟嵌入**（delay embedding，即把序列按固定间隔折叠成二维矩阵）变成一张「图像」，然后直接用图像扩散模型（EDM 损失 + UNet + EMA）去生成，最后把图像反变换回序列。这里 **EDM** 指 Karras 等人给出的那一套扩散训练/采样参数化，**EMA** 指训练权重的滑动平均。只要延迟与边长选得使折叠**可精确逆转**，这个变换就不丢信息。

**怎么跑的、改了什么。** 延迟嵌入变换、UNet、EDM 损失、EMA、反向过程全部未改。偏离有五处：

1. 写了 `data/long_range.py` 与 `data/data_provider/`——仓库把 `data/` 作为空包发布（语料另发），这是它预留的扩展点，不算改代码；
2. 逐动作穷举出能把方阵**恰好填满**因而可逆的 (延迟, 边长) 组合：tap (2,8)、pinch (6,16)、swipe (11,16)、scroll (13,16)、keystroke (16,32)。tap 的窗长 T=16 无精确解，用最小的方阵加两列零填充，仍然精确可逆；
3. 逐通道 min-max 归一化到 [0,1]——作者所有语料都这样处理，且 EDM 里写死的 `sigma_data = 0.5` 就是按这个前提配的；
4. 写了训练驱动与采样器。作者的 `run_unconditional.py` 每次评估要重训十次 S4 分类器（S4 是作者用来算评估指标的那个序列分类器，不参与生成）、且只在评估改善时存盘，仓库里**根本没有采样脚本**；
5. 用作者自己 `mujoco.yaml` 里那个更窄的 UNet（1440 万参数而非 1.517 亿；实测五个动作的参数量在 1430 万–1477 万之间）。这是作者提供的一种配置选择，不是模型改动。

**预算与早停（这是要主动交代的短板）。** 作者定的是固定 1000 epoch，实测约 79 GPU 小时/动作，跑不起。改成每 25 epoch 用「lag-1 自相关 + 逐通道离散度 + 窗口摘要能量距离」与真人数据比一次，连续 3 次不改善就停。**采样用的是停下那一刻的模型，不是历史最优检查点**（代码只有一个反复覆盖的检查点文件）。逐动作：tap 停在 574（gap 0.370，最优是 epoch 499 的 0.361；**gap** ＝ 把上面这三项——lag-1 自相关、逐通道离散度、窗口摘要能量距离——合成的一个综合距离，越小说明生成样本越接近真人，§7.1 有同一定义）、pinch 停在 399（0.399 / 324 的 0.373）、swipe 停在 374（0.421 / 299 的 0.352）、scroll 停在 449（0.427 / 374 的 0.334）、keystroke 停在 424（0.778 / 349 的 0.568）。keystroke 差了约 37%。**结论是这个基线被略微低估了**，最优权重已被覆盖找不回来，要消除这条限定只能重训。

**结果。** 30 格，均值 **0.683**、中位 0.778、20 格过 0.60。这是第三方方法里唯一进入发布版同一量级的：第二名（Diffusion-TS 轨迹臂）是 0.460，它是其 1.5 倍；在 IMU 这条通道上第二名（Diffusion-TS IMU 臂）只有 0.325，差距超过两倍。它甚至逼近了真人对照的 0.773——也就是说在多数格子上，把它的假 IMU 灌进去，和把真人窗口灌进去差别没有想象中大。**所以「第三方方法都很弱」这个说法不成立**，正确的说法是：只有「现代扩散 + 图像变换」这一类能接近，且仍比发布版的 0.835 低 0.152。

它的短板在哪里也很清楚：逐检测器看，behaveformer_stdat 0.869、hmog_style_svm 0.847、paper_svm 0.816 都很高，但两个树模型垮了——hmog_style_rf 只有 0.464、paper_xgboost 0.491，而发布版在同两个检测器上是 0.821 和 0.774。逐动作则是 tap 0.871 最高、keystroke 0.533 最低。

**这里曾有一处口径不一致，现已消除**：`final/imagentime/README.md`（仓库副本 `comparison/notes/imagentime.md`）一度是格子没跑齐时生成的快照，数字与 `RESULTS.md` 对不上；成稿前该文件已按 30 格齐全后的产物重新生成，现在说明、`RESULTS.md` 表 1 与本节三处一致，同为 **30 格 / 均值 0.683 / 20 格过 0.60**（§7.7 记的是同一件事）。

### 3.4 TTS-GAN（AIME 2022）

**是什么。** Li 等人的 TTS-GAN 是一个纯 Transformer 的生成对抗网络：生成器把噪声变成一段时间序列，判别器判真假，两者对抗训练。它不是扩散模型，训练更快但更不稳定。

**怎么跑的、改了什么。** Transformer 生成器与判别器、训练循环、EMA、学习率调度全部未改，作者的逐窗口 z-score 归一化也照用。两处偏离：

1. **加了训练中途的检查点**——作者的循环在 epoch 之间什么都不存，中断即全丢；
2. **上调了训练预算**。第一次跑完发现明显欠训：其 lag-1 自相关（相邻采样点之间的相关系数，衡量信号有没有时间连续性）只有 0.387–0.850，而真人数据是 **0.947–0.996**（本文所有真人 lag-1 一律用 §3.7 那一列的现算值；`comparison/notes/ttsgan.md` 与 `ttsgan_budget_evidence.json`（后者未发布）里记录的原值是 0.945–0.996，逐动作与现算差 ≤0.002，是同一个量的两次计算，不是两个测量）。**这个决定的证据被完整留在 `ttsgan_budget_evidence.json` 里**，文件本身写明了理由：一个输出点与点之间毫无相关性的生成器可以被平凡地区分出来，从它算出的 FAR 描述的是训练预算而不是这个方法。留档之后，报告的结果就不能被读成「对第一次那个小预算的评价」。实际预算从 8000/20000/15000/15000/30000 次迭代（keystroke/pinch/scroll/swipe/tap）提到 48000/80000/60000/60000/45000 次，对应 441/741/551/556/672 个 epoch。

**结果。** 加了预算之后仍然是全场最低：30 格，均值 0.124、中位 0.008、只有 1 格过 0.60。逐检测器全线在 0.087–0.230 之间；逐动作只有 tap 0.463 有点样子，scroll 0.015、swipe 0.022、keystroke 0.002 基本等于被全部拦下。

### 3.5 pyclick（贝塞尔曲线拟人光标库）

**是什么。** pyclick（MIT 许可）是开源界的参考实现：在起终点之间的包围盒里随机撒几个内部控制点，穿过它们画一条**贝塞尔曲线**（由控制点决定形状的光滑曲线），再给每个点加高斯扰动，最后用一个缓动函数塑造速度曲线。这就是攻击者不花任何代价就能拿到的东西。

**怎么跑的、改了什么。** `HumanCurve` 及其扰动/缓动未改。唯一的偏离：库在模块层 `import pyautogui` 但这条路径上根本不用它，于是注册一个空模块替身（stub）满足这个 import，不碰库本身。驱动侧只提供起终点、点数和逐事件随机种子，再把像素坐标换算回分片的归一化坐标（屏幕按 HMOG 用的 Galaxy S4，1080×1920，横屏时对调）。

**关于「注入率」。** 检测器读的是 100 Hz 的等距网格，而触摸事件的更新比这慢，所以一条真实划动会在大约一半的行上原样重复上一个坐标——这个「哪几行是新坐标」的模式就是注入率的可观测形态，本身就是一个极强的判别特征（一个每行都给新坐标的生成器在这个统计量上和真人差得一眼可辨）。掌握受害者录音的方法（包括本方法）直接继承受害者自己的更新节奏（实测真人约 scroll 55 Hz、swipe 51 Hz）；pyclick 和 ghost-cursor 这两个库**不掌握任何受害者数据**，没有可继承的录音，只能自己选一个注入率。这里统一选 **Android 系统自身的派发频率 60 Hz**（`UiDevice.swipe` 每个垂直同步周期派发一个 MOVE，`hmog_event_builder.py:72` 的 `ANDROID_INJECTION_HZ = 60.0`），而不是照抄从受害者样本里测出来的那个值——照抄等于把「基线本来就不该拥有的受害者信息」偷偷还给它。

**keystroke 被 declined**：按键在检测器网格上的「轨迹」是一串位置恒定的按住，两点之间根本没有路径，光标路径生成器无从产出；替一个作者从未提出的东西上去测的是稻草人。因此是 4 个动作 × 6 个检测器 = 24 格。

**结果。** 24 格，均值 0.294、中位 0.198、6 格过 0.60。tap 0.687 最高，scroll 0.143、swipe 0.140、pinch 0.207。

### 3.6 ghost-cursor（Fitts 定律拟人光标库）

**是什么。** ghost-cursor 是浏览器自动化生态里用得最多的拟人指针库。相比 pyclick 多两件事：采样点数由 **Fitts 定律**（移动时间随距离增长、随目标尺寸缩小的经典人因定律）推出来，因而长距离移动帧数更多；以及超过阈值的移动会**先冲过目标再修正回来**，这是真人指点的真实特性，单条贝塞尔曲线做不出来。

**怎么跑的、改了什么。** 原库是 TypeScript 且驱动浏览器，所以用的是移植版，其 `bezierCurve` / `generateBezierAnchors` / `fitts` / `clamp` / `overshoot` 已逐行对照 `spoof.ts`、`math.ts` 核对一致。**两处移植错误被更正，并且都写进了 README**：

1. **采样方式**。原库取 `curve.getLUT(steps)`，按**弧长**等距；移植版用 `linspace(0,1,steps)`，按贝塞尔**参数**等距。曲线上两者不同：在一段 600 像素的弧上取 12 个点，移植版的步长从 81.9 递减到 68.1 像素（最快是最慢的 1.20 倍），原库则平坦在 72.8。每步距离就是速度曲线，而速度曲线正是检测器读的东西——不改就等于测了一个 ghost-cursor 从不产生的速度模式。
2. **`spreadOverride` 被移植版丢掉了**。原库写的是 `spreadOverride ?? clamp(...)`：调用方可以指定一个更小的控制点散布。移植版把这个参数整个丢了，永远走 `clamp(...)`。这不是无关紧要的：`move()` 的冲过头（overshoot）修正第二段正是靠 `spreadOverride = OVERSHOOT_SPREAD` 把散布收紧才「修正」得回来，丢了它，overshoot 就名存实亡。所以在 `ghost_cursor_path.path()` 里恢复了这个参数（带 override 时用 `_curve_with_spread()` 重建曲线）。

**要说清楚哪一项不是更正**：冲过头本身（`move` 里超过阈值就调两次 `path`，先到目标附近一个散布点、再收紧散布回到目标）是按 `spoof.ts:688-700` **忠实复现**的，`comparison/notes/ghostcursor.md` 把它列在 "What ran unchanged" 一栏，不算移植错误。真正被记为 `port_deviations_corrected` 的就是上面两项：弧长采样、以及被恢复的 `spreadOverride`。

另有一个**退化路径（起点与终点重合，没有可画的轨迹）**的保护：库的锚点构造要对起点到中点的向量做归一化，两端重合时会除以 0，所以这里直接返回常数点，并记为 declined-by-degeneracy 而不是让它崩溃。ghost-cursor 自行决定输出多少个点，我们按下标均匀重采样到载体那条事件的行数；由于库的点本来就按固定时间间隔派发，均匀重采样不改变速度曲线的形状。keystroke 同样 declined，理由与 pyclick 相同。

**这类退化事件有多少条，未测量。** 产物里没有单独的计数：`baseline_counts.json` 记的是 `trajectory_swapped` / `trajectory_declined`（后者是「这条 bundle 没有替换轨迹的事件数」，即本 bundle 不拥有的动作加上被 declined 的 keystroke，例如 tap_and_pinch 是 swapped 40000 / declined 60000）和 `trajectory_clipped_samples`（值为 0），**没有 declined-by-degeneracy 这一项**；`bundle_manifest.json` 与 build/verify 日志里也没有。所以「ghost-cursor 的 0.335 里有多少来自常数坐标事件」这个问题现在答不了，只能标未测量；要回答必须在 `ghost_cursor_path.path()` 里加计数并重跑构建。（顺带一提，方向上并不一定是压低分数：它逐动作最高的恰好是 tap 0.831，而 tap 正是最可能触发退化保护的动作。）

**结果。** 24 格，均值 0.335、中位 0.232、6 格过 0.60。tap 0.831，其余三个动作在 0.153–0.183。

**这两个库不是竞争者。** 它们不含任何学习成分，没有见过任何受害者数据，是确定性曲线生成器。它们的作用是给出「非学习方法能做到什么程度」的**下界**：即使把 tap 这种几乎没有路径可言的动作算进去，均值也只有 0.294 / 0.335；除 tap 外的三个动作全部塌到 0.14–0.21。

### 3.7 为什么弱的那几个弱：两种可量化的失效模式

Diffusion-TS 和 TTS-GAN 的低分**不是「参数没调好」，而是两种方向相反、都能直接测出来的失效**。下表左半列是「生成样本的通道标准差 ÷ 真人同通道标准差」（1.0 表示离散程度一致），右半列是 lag-1 自相关（时间连续性）。

| 动作 | 真人 lag-1 | Diffusion-TS: std 比 / lag-1 | CSDI: std 比 / lag-1 | ImagenTime: std 比 / lag-1 | TTS-GAN: std 比 / lag-1 |
|---|---|---|---|---|---|
| tap | 0.947 | 0.762 / 0.951 | 0.507–0.891 / 0.954 | 0.891–1.004 / 0.909 | 0.964–1.084 / 0.862 |
| scroll | 0.996 | 0.643 / 0.996 | 0.428–0.664 / 0.998 | 0.832–1.034 / 0.987 | 0.998–1.055 / 0.729 |
| swipe | 0.996 | 0.659 / 0.995 | 0.478–0.764 / 0.997 | 0.813–1.019 / 0.987 | 0.971–1.034 / 0.745 |
| pinch | 0.990 | 0.709 / 0.992 | 0.526–0.821 / 0.992 | 0.873–1.030 / 0.980 | 0.990–1.023 / 0.910 |
| keystroke | 0.971 | 0.561 / 0.956 | 0.382–0.626 / 0.991 | 0.739–1.074 / 0.966 | 0.949–1.004 / 0.364 |

（Diffusion-TS 那一列给的是六个通道比值的**中位数**，其余给区间。std 比来自各方法自己的 `summary_*.json` 里已存的 `generated_std` / `real_std`；lag-1 是用项目自带的 `convergence.py::lag1` 对已存样本 `samples_*.npy` 现算的。可信度校验：同一段代码算出的**低预算** TTS-GAN 值为 0.851/0.478/0.481/0.523/0.388，与 `ttsgan_budget_evidence.json` 里记录的 0.850/0.479/0.482/0.522/0.387 逐动作差 ≤0.001。）

- **Diffusion-TS：方差不足。** 时间连续性完美（lag-1 与真人几乎重合），但生成样本的离散程度系统性偏小，六通道比值中位数只有真人的 0.561–0.762 倍；陀螺仪三轴最严重，swipe 低到 0.477、keystroke 低到 0.298。也就是说它画出的是一条「太乖」的曲线——形状对、动态范围不够。CSDI 是同一类失效且更重（scroll/keystroke 的加速度通道只有 0.38–0.44 倍），它的分数（0.292）也确实和 Diffusion-TS IMU 臂（0.325）在同一档。
- **TTS-GAN：几乎没有时间相关性。** 方向正相反——边缘分布的离散度几乎完美（比值 0.949–1.084），但相邻采样点之间的相关性远低于真人：scroll 0.729、swipe 0.745 对真人的 0.996，keystroke 只有 0.364 对真人的 0.971。它生成的是统计量对得上、但时间上抖动的信号，任何读时序结构的检测器都能一眼看穿，这与它 0.124 的均值、0.008 的中位数完全吻合。注意这是**已经上调预算之后**的数字：低预算时 keystroke 是 0.388，加了 6 倍迭代只到 0.364，说明这不是预算问题。
- **ImagenTime 两项都对**（离散度 0.739–1.074、lag-1 与真人差 0.005–0.038），这就是它能进入同一量级的机制性解释。

最后一条要提醒的：**在这个区间里，「生成质量指标」对攻击成功率没有判别力**。

先把这个指标交代清楚，否则没法判断两个数之间的差是不是噪声。用的是 TimeGAN 系列的**判别分数**，代码是 Diffusion-TS 作者自带的 `Utils/discriminative_metric.py`：训一个事后 RNN 分类器区分真假，输出 `|准确率 − 0.5|`。**0 表示完全分不出**（分类器只能瞎猜），上限 0.5 表示完全分得开。「真人对真人」的对照是这样切的：把同一批真人窗口随机置换后取互不重叠的两半（各 n = 1000 条），对这两半跑同一套指标——它给出的是**这份数据本身允许的地板**，而不是 0。每个数都是 3 次重复（种子 42/43/44）的均值，`quality_diffts/quality_*.json` 里存了逐次的原始值（本小节引用的 `quality_*` 产物与日志**都在内部实验树里，未发布**）。

Diffusion-TS 的 HMOG 轨迹样本（`quality_diffts/quality_*_trajectory.json`，未发布）：

| 动作 | 生成 vs 真人 | 真人 vs 真人（对照） |
|---|---|---|
| tap | 0.012 ± 0.003 | 0.016 ± 0.007 |
| pinch | 0.018 ± 0.010 | 0.015 ± 0.009 |
| swipe | 0.030 ± 0.032 | 0.006 ± 0.001 |
| scroll | 0.029 ± 0.017 | 0.023 ± 0.007 |
| keystroke | 0.400 ± 0.009 | 0.021 ± 0.021 |

（± 是 3 次重复的标准差。）除 keystroke 外，四个动作上「生成」与「对照」之差都在 0.002–0.024 之间，而重复本身的标准差就有 0.001–0.032——**差值落在噪声里**。同一个「真人对真人」量在两次独立跑里也不稳定：tap 的 IMU 对照在 `quality_ttsgan.log` 里是 0.008，在 `quality_diffts.log` 里是 0.022。所以正确的说法不是「Diffusion-TS 比真人对真人还难分」，而是：**判别分数已经饱和到与真人对照同一量级，在这个区间内无法再区分这几个方法**——而它们在检测器上的 FAR 相差 0.336（Diffusion-TS 轨迹臂 0.460 对 TTS-GAN 0.124）。TTS-GAN 也一样：tap 0.038、pinch 0.014（`quality_ttsgan.log`，同一批对照 0.008 / 0.022），FAR 却是全场最低。

要公平地说，这个指标**并非全无信号**：keystroke 轨迹上它读到 0.400，离对照的 0.021 有二十倍，明确报警，而 Diffusion-TS 轨迹臂的 keystroke 恰好也是它逐动作 FAR 最低的一个（0.201）。失效的是它在 0.006–0.040 这个饱和区内的分辨力，不是它在任何情况下都没用。这也是本文坚持用 FRR=5% 阈值上的 FAR 而不是用生成质量指标做主判据的原因。

**还有一条限定必须写在这里。** 四个学习型基线里，**只有 Diffusion-TS 的训练通路对着作者自己的基准复现过**（Sines 判别分数 0.0108 ± 0.0061 对论文的 0.006 ± 0.007，见 §3.1）。CSDI、ImagenTime、TTS-GAN 三个的 README 里 "Sanity check" 一节记的都是**内部一致性证据**——CSDI 是「装真包所以 `diff_models.py` 与作者文件逐字节一致、`target_strategy` 留 `random` 免得损失恒为 0」，ImagenTime 是「采样前先推一个真实 batch 过 `ts_to_img`，否则反填充形状错」，TTS-GAN 则连这一节都没有，只有预算证据文件——**没有任何一处把它们在原论文自己的语料上的指标复现出来**。也就是说，对这三个方法，「它们弱是因为我们的接法有问题」这个竞争解释**没有被排除，属于未测量**。§3.3、§3.7 那个「第三方方法弱在生成质量」的主张，严格成立的范围只到 Diffusion-TS；对另外三个，它是一个未经原论文基准校准的推断。

## 4. 方法自身的消融：A1 到 A7

### 4.1 消融实验是什么，为什么必须做

「消融实验」（ablation study）指的是：保持整套系统不动，一次只拿掉或改掉**一个**部件，重新跑完整
评测，看指标掉多少。掉得多，说明那个部件在起作用；掉得少甚至不掉，说明它可以删掉，或者它的功劳其实
是别的部件在担。

对本文这类「多部件叠出来的方法」而言，消融不是锦上添花，而是唯一能反驳这个质疑的证据：**是不是只有
某一个部件在撑场面，其余都是装饰？** 第 3 节的对比实验只能说明「我们的整体比别人强」，它无法区分
「五-shot 条件 + 对抗训练 + 梯度合并三者协同」和「其实只有五-shot 有用」。A1–A7 就是用来做这个区分的。

判据沿用全文口径：**在开发集选定的 FRR=5%（错误拒绝率 5%）阈值上的 FAR（假接受率，false accept
rate）**。FAR 越高，说明伪造样本越多地被检测器当成真人放行，攻击越成功。每个臂都**重新训练一遍它自己
的检测器**——检测器是拿这个臂产出的伪造样本训的，不是拿发布版的检测器去打它。所以臂之间的比较是公平的
「各打各的」，不是迁移。

本节报告两个量：

- **均值**：该臂所有格子的 FAR 平均。
- **配对差（vs 发布版）**：把该臂覆盖的格子挑出来，取发布版在**同一批格子**上的 FAR，逐格相减再平均。
  正号 = 该臂比发布版弱 = 被拿掉的部件确实在贡献。配对差比均值可靠得多，因为它免疫「不同臂覆盖的格子
  数量不同」这个陷阱。

### 4.2 为什么只有 IMU 通道、为什么是 24 格不是 30 格

**只报 IMU（惯性）通道**：A1–A7 改的全是 IMU 生成器，没有一个臂碰过触摸坐标。轨迹通道和联合通道的格子
里，轨迹那一半仍然是发布版原样的数据，把它们算进来只会把差异稀释掉。

**keystroke（按键）被按构造排除，这不是遗漏。** 发布版的 keystroke 伪造 IMU **根本不经过扩散生成器**：
它的元数据里写着 `diffusion_used: false`、`model_used: false`，生成来源是
`security_exp/keystroke_imu_pulse.py`——一个由受害者自己真实按键事件驱动的**解析式适配器**。既然
keystroke 的 IMU 从未经过扩散生成器，那么任何针对扩散生成器的消融都**动不了它一格**。
建库脚本 `build_ablation_cache_baseline.py` 因此直接把 keystroke 声明为 declined（拒绝报数），而不是
让它进表格。理由写在该文件的文档字符串里，值得原样引用其含义：一个恒为 0 的差值会被读成「这个部件对
keystroke 没帮助」，而事实是「这个消融根本够不着 keystroke」。两句话的含义完全不同，留空比填 0 诚实。

排掉 keystroke，剩下 tap / scroll / swipe / pinch 四个动作 × 六个检测器 = **24 格**，这就是 A2–A6 的
分母。（另外 A3 的 keystroke 连检查点都没有，README 里单列为 "Actions without a checkpoint"，属于
双重排除。）

### 4.3 七个臂的总表

发布版在这 24 格上的参考值（IMU 逐动作）：tap 0.881、scroll 0.726、swipe 0.852、pinch 0.883。

下表「采样协议」一列填的是项目内部的协议名，命名规则是两段拼接：`noshot` / `fewshot` 表示**采样时给不
给参考样本**，后缀 `_adv` 表示**训练时开不开对抗目标**。因此 A1 = `fewshot_adv`（有参考 + 有对抗）、
A2 = `noshot_adv`（无参考 + 有对抗）、A3 = `fewshot`（有参考 + 无对抗）。

|---|---|---|---|---|---|---|

### 4.5 A4–A6：k_refs 曲线的形状

把参考条件数 k 从 0 扫到 8：

```
k = 0 (A2)  0.779
k = 1 (A4)  0.798
k = 3 (A5)  0.832
k = 5 (A1)  0.835   ← 发布版
k = 8 (A6)  0.830
```

单调上升，k=3 之后**基本走平**：k=3 / k=5 / k=8 三点是 0.832 / 0.835 / 0.830，两两相差不超过 0.005。

**这里必须先交代一条循环性，否则"落进噪声里"是空话。** 本项目**没有做重复种子实验**——每个臂只跑过
一次，磁盘上不存在同一配置的第二次运行，因此**重训方差**（同一份配置换个随机种子重训会差多少）
**从未被测量**。全文反复引用的 **0.005**，是拿 A1（k=5）、A5（k=3）、A6（k=8）三个臂的离散度**当作**
噪声的代理估计；这三个臂共用同一个检查点、只改采样参数（见本节末那条限定），所以它量到的**只有采样
层的随机性**。而"这三个臂本应给出相同结果"这个前提，恰恰就是"k 在 3 处已饱和"这个待验证的结论本身。
**用饱和假设估出噪声，再用噪声论证饱和，是循环的。**

**全文对 0.005 只有下面两句话，不存在第三种读法（§5.6、§7.2 逐字沿用同一对措辞）：**

- 对 A1、A4–A6 这类**共用同一个检查点、只改采样参数**的臂，**0.005 是采样层噪声的上界**——若 k 其实
  没饱和，A1/A5/A6 的离散度里就掺了真实的 k 效应，纯采样噪声只会比 0.005 更小。
- 对 A7–A11 这类**重新训练**出来的臂，它们之上还叠着一层未测量的重训方差，所以
  **0.005 是总噪声的下界**，真实的显著性门槛只会比它高，不会更低。

两句话说的是两个不同的量（一个采样层、一个含重训方差的总噪声），不构成矛盾。本节的饱和论断只能用第
一句；而那条循环性对它是实打实的——用上界去论"分不开"在方向上是**保守**的，但"只有噪声的 1.7 倍"这个
具体倍数不可当真。**§7.2 应把这条一并记为局限**——那一节继承的正是这个 0.005。

在这个限定下能说的只有：**k=3 到 k=8 之间没有测出可分辨的差异，三条参考很可能就够了**，发布版选 5 是
安全余量而非必需。要把它坐实，需要的是同一配置换随机种子重跑若干次，本项目未做。

**一个必须写出来的限定：A4/A5/A6 测的不是「为该 k 训练的模型」。** 检查点是在各自协议自己的参考数量
下训练的（发布版即 k=5），A4–A6 只是在采样时把 k 改成 1/3/8，模型没有重训。所以这条曲线量的是**参考
编码器的泛化能力**——在训练时没见过的参考条数下还能不能用——而不是「若从头按 k=1 训练会怎样」。
这个限定已经固化在采样器写出的 `ablation.json`（未发布）的 `k_refs_note` 字段里，并被自动搬进
`ablation/notes/abl_krefs1.md`、`abl_krefs3.md`、`abl_krefs8.md` 三份说明的
"What this arm does not measure" 一节，原文是：checkpoints were trained at their protocol's own
reference count; sampling at a different count measures how the reference encoder generalises, not a
model trained for that count。

（附带一条口径纠正：项目笔记 `RESUME_BASELINES_CN.md`（未发布）的 0.11 节里留有一个更早的 k=3 读数
0.813，那是缓存未跑满时的中间值；以 `RESULTS.md` 与 `ablation/notes/abl_krefs3.md` 一致的
**0.832** 为准。）

### 4.6 A7：梯度合并机制 —— 本节最重要的一个臂

**被消融的是什么。** 发布版训练时有两个目标：重建目标（让伪造 IMU 像真的）和对抗目标（让判别器分不
出来）。常规做法是把两个标量损失加权相加再反传。发布版不这么做，它在**梯度层面**合并，具体三件事，
全在上游 `final_gen/train.py::backward_with_projected_adversarial_gradients` 里：

1. **分开反传**：重建损失单独反传一次，保留一份干净完整的重建梯度 `g_recon` 作为参照系；
2. **冲突投影**：仅当对抗梯度与重建梯度点积为负（`dot(g_adv, g_recon) < 0`，即两者方向相抵）时，把
   `g_adv` 中与 `g_recon` 冲突的那个分量投影掉；
3. **相对范数上限**：把剩下的对抗贡献钉到重建梯度范数的固定比例 `max_grad_ratio · ‖g_recon‖`，每一步
   重新计算。

**A7 怎么关掉它——不改上游一行代码。** 设 `project_conflicts: false` 且 `max_grad_ratio: 1e9`（大到
永远不会触发），代码路径就在**代数上退化**成加权相加：`projection_coeff = 0`、
`merge_scale = clamp(inf, max=1) = 1`，于是 `p.grad = g_recon + g_weight · g_adv`。这里的 `g_weight`
就是 `effective_config.json` 里的同名字段（对抗项的固定权重），不是本节新引入的符号。冒烟日志已逐位
核对确认：`merge_scale = 1.0`、`projected_norm == raw_norm`。逐动作的其余超参照抄发布版**实际运行**的
`effective_config.json`：scroll 与 swipe 都是 **`g_weight` = 0.04、`max_grad_ratio` = 0.5**——两个不同的
量，别对调，第 5 节从 `plan.json` 读回的底座是同名同值的这两个数。A7 只把 `max_grad_ratio` 顶成 1e9，
`g_weight` 原样保留，diff 只有上述两处。

**训练日志显示两道保护各起多少作用**（统计自 25 个 `fewshot_adv` 运行）：冲突投影在 0–25% 的步上触发，
多数动作 <1%；范数上限则**每一步、每个动作、每次运行都在起作用**，中位 `merge_scale` 落在 0.005–0.07，
也就是把对抗梯度压小 **15–200 倍**。因此 A7 关掉的实际主体是那道上限，投影是补充。

**结果：12 格均值 0.734，配对差 +0.054，只有 9/12 格 ≥ 0.60。**

**逐检测器才是机制所在，只看均值会错过全部信息。** 下表两行**严格同格**：A7 只覆盖 scroll 与 swipe，
所以 A1 那一行取的也是发布版在**同样这 12 格**（scroll+swipe × `imu_only` × 6 检测器）上的均值，
**不是** 4.4 节那张表里的 24 格 A1 行（后者是 0.878 / 0.822 / 0.881 / 0.769 / 0.848 / 0.816，
覆盖 tap/scroll/swipe/pinch 四个动作，**不能拿来和 A7 相减**）。本表口径与 §5.7、以及 `RESULTS.md`
逐检测器表的分块完全一致。

| | HMOG-SVM | HMOG-RF | Paper-SVM | Paper-XGB | BehaveFormer | AuthConformer |
|---|---|---|---|---|---|---|
| A1（发布版，scroll+swipe，12 格） | 0.859 | 0.772 | 0.852 | 0.725 | 0.775 | 0.749 |
| A7（scroll+swipe，12 格） | **0.901** | **0.581** | 0.824 | **0.607** | 0.859 | **0.634** |

三类检测器塌了：HMOG-RF 0.772 → 0.581、Paper-XGB 0.725 → 0.607、AuthConformer 0.749 → 0.634。
两个 SVM **不降反升**：HMOG-SVM 0.859 → 0.901，Paper-SVM 只微降到 0.824；BehaveFormer 从 0.775
升到 0.859。

这说明的**不是「整体变差」**，而是：加权相加让某类**结构性线索重新暴露**在伪造样本里，而那正是轴对齐
树模型和 conformer 能抓、**线性 SVM** 抓不到的东西（按 §1.5，本文两个 SVM 都是线性的，`hmog_style_svm`
就是 `LinearSVC`，此处不涉及核方法）。机制上：线性 SVM 只看特征空间里的**一个线性方向**，重新暴露的
线索若不落在那个方向上它就看不见；轴对齐的树模型能对**单个统计量切区间**，conformer 能看**局部时序
模式**，因此先崩的是后两类。梯度层面的投影 + 范数上限保护的就是这类线索不被对抗目标撕出来。这与项目中另一处独立发现（float32 时钟指纹：非树检测器全好、树模型全崩）是同一类现象——
树模型对特定统计量异常敏感，因此它是本方法最灵敏的探针。

### 4.7 A7 的格子数：12 不是 24，均值不能横向比

A7 是**唯一需要重训生成器**的消融（A2/A3 换协议重训，A4–A6 连训练都不用；A7 改的是训练时的梯度合并
路径，只能重训）。受算力所限，**A7 只重训了 scroll 和 swipe 两个动作**，tap 与 pinch 在建库时被显式
声明为 declined（它们同属 `tap_and_pinch` 这一个 bundle），keystroke 照 4.2 节的理由排除。
于是 2 动作 × 6 检测器 = **12 格**。同样的两动作范围也适用于后续的 A8–A11 critic 消融臂，
它们的结果见**第 5 节**：`RESULTS.md` 表 2 **已收录 A7–A11 的完整数字**（12 格的均值、配对差、
≥0.60 计数），没有任何一行标 *not finished*；第 5 节报的数字是从冻结的逐格产物按同一口径
（`thresholds.json` 的 `frr5` 切点 + `test_scores.jsonl`）重算的，与该表**逐位一致**，
两条独立路径互为交叉校验。

## 5. 把对抗机制拆成部件：A8–A11

本节把对抗训练拆成四个部件，其中三个是 **critic**（即判别器：一个学着区分真假的小分类网络，
配置里写作 `adv.critics.{feature,set,waveform}`），第四个是不含对抗博弈的直接匹配损失
`feature_match`。A8–A11 这四个臂各拿掉其中一个，其余三个原样保留。

### 5.1 A3 留下的问题

消融臂 A3（"关掉对抗训练"）在 24 个格子上测得均值 0.802，对照发布版 A1 的 0.835，配对差 **+0.034**。
这个数说明整套对抗机制值多少，但它是一个标量：0.034 里哪一份来自哪个部件，A3 答不出来。
A8–A11 就是为了把它拆开——每个臂只拿掉一样东西，其余三样原样保留，四个数应当能对应到四个部件。

### 5.2 为什么是四个臂，不是三个

配置文件里 `adv.critics` 底下只有三个开关：`feature`、`set`、`waveform`。按配置结构看，三个臂就够了。
但训练器里还有第四样东西——`feature_match`（直接特征匹配损失）。它**不在** `adv.critics` 里，
而是写在 `final_gen/train.py` 中，只由 `adv.feature_match_weight > 0` 单独控制。
关键在于：它位于同一个 `adv_update` 块内，它的加权损失和三个 critic 的损失一起汇入同一条梯度，
经过同一套梯度投影与范数上限处理。**所以 A3 关掉的是四样东西，不是三样。**

只做三个 critic 臂会有两个后果。第一，0.034 里会有一块无人认领，三份加起来对不上账。
第二个更糟：A8（关掉 feature critic）会测出一个**偏小的假效应**。因为 feature 通路并没有被真正切断——
critic 关了，直接匹配损失还在，还在往生成器里供给同一批统计量。补上 A11（把 `feature_match_weight`
置零、三个 critic 全留）之后，这条通路的两半才都被覆盖，账才闭合。

四个臂在 `run_critic_ablation.py` 的 `ARMS` 表里定义，逐一对应：
A8 关 `critics.feature`、A9 关 `critics.set`、A10 关 `critics.waveform`、A11 把 `feature_match_weight` 置 0。

### 5.3 四个部件分别是什么

- **feature critic**：一个判别器（discriminator，就是一个学着区分真假的二分类小网络）。
  它不看波形本身，只看一个窗口的分布统计量——标准差、偏度（skewness，分布左右不对称的程度）、
  峰度（kurtosis，尾巴有多重）、以及六个传感器通道两两之间的相关性。
- **waveform critic**：另一个判别器，直接把整段信号丢给它判真假，不做任何统计摘要。
- **set critic**：判别对象是**五条参考构成的集合整体**。本方法用受害者的五条真实窗口作为条件
  （five-shot），set critic 要求一条伪造样本不仅单独看起来像真人，还要"属于"它那五条参考——
  换句话说，它管的是与受害者的一致性，而不是普遍意义上的真实性。
- **feature_match**：不是判别器，是一个直接的统计匹配损失。它把可微版本的 HMOG 特征
  （均值、标准差、偏度、峰度、通道间相关，日志里对应
  `adv_feature_match_mean/std/skew/kurt/corr`）往真实值上拉，不经过任何对抗博弈。

### 5.4 基线配置（base config）取自发布版，不是 A7 的配置

A7（另一个消融臂）关掉了梯度保护（`project_conflicts: false` 加上放开的 `max_grad_ratio`）。
如果从 A7 的配置文件出发再翻 critic 开关，一次就改了两样东西，测出来的数没有意义。
所以这四个臂的**基线配置**（base config，即翻开关之前的那份出发点配置）是**发布版那次运行自己的
`effective_config.json`**，梯度保护保持开启，只翻一个开关。

`run_critic_ablation.py` 里写了硬断言：若基线配置的 `project_conflicts` 不是 `True`、
或 `max_grad_ratio` 不等于 `0.5`，直接 `SystemExit` 并提示"这看起来是 A7 的配置而不是发布版的"。
另有两条断言防止空转：要关的 critic 在基线配置里若本来就不是 `true`，或 `feature_match_weight` 本来就不大于 0，
同样直接中止——"没有东西可以给这个臂拿掉"。

`plan.json`（未发布，随臂的内部产物）记录了每次改动的前后值，可逐条核对：scroll 与 swipe 的
`gradient_protection` 均为 `{project_conflicts: true, max_grad_ratio: 0.5, g_weight: 0.04}`；
critics 三元组从 `{true,true,true}` 变成只有一项为 `false`；
A11 的 `feature_match_weight` 从 scroll 的 0.03、swipe 的 0.02 改为 0.0。
训练轮数取发布版自己的（scroll 160 epoch、swipe 156 epoch），batch size 128。
只有 scroll 和 swipe 需要重训，所以每个臂是 **12 格**（2 动作 × 6 检测器）而不是 24 格。

### 5.5 开关确实生效：从训练日志读回的证据

只核对配置文件不够——配置写对了、代码路径没走到也是可能的。所以证据从真实训练日志里读回
（`ablations/<arm>/train_{scroll,swipe}.log`，逐步打印的 JSON 行；**这批日志未发布**——
仓库 `.gitignore` 硬排除 `**/*.log`，下面的计数是在作者机器上数出来的）。

训练日志每一步打印一行 JSON，**`adv_acc_<name>` 是名为 `<name>` 的那个 critic 在当前这一步的
判别准确率**（0.5 表示它完全分不出真假）。某个 critic 被关掉之后，它的 `adv_acc_*` 键就不再出现在
JSON 行里——这正是我们用来验证开关真的生效的信号；同理 `adv_feature_match_*` 那组键在
`feature_match_weight` 被置零后整组消失。

| 臂 | 日志里出现的 `adv_acc_*` | `adv_feature_match_*` 项 |
|---|---|---|
| A8 关 feature critic | 只剩 `adv_acc_set`、`adv_acc_waveform` | 仍在（这正是需要 A11 的原因） |
| A9 关 set critic | 只剩 `adv_acc_feature`、`adv_acc_waveform` | 仍在 |
| A10 关 waveform critic | 只剩 `adv_acc_feature`、`adv_acc_set` | 仍在 |

计数是逐行统计的：scroll 日志里 A8 的 `adv_acc_set` / `adv_acc_waveform` 各 606 次而

这组交叉对照同时证明了两件事：开关翻对了，以及 A8 确实没有切断 feature 通路的直接匹配那一半。

### 5.6 先说清统计功效——这一段不能跳过

臂均值的**采样层波动约 0.005**。这不是估计，是用 A1、A5、A6 三个本应几乎相同的臂量出来的：
k_refs（参考条数）在 3 处已经饱和，所以 A5（k=3）和 A6（k=8）与 A1（k=5，发布版）在理论上应当一致。
实测配对差是 A5 **+0.004**、A6 **+0.005**，两者之间 **+0.002**。这三个数刻画的就是"什么都没真的改变"时
的测量抖动。

**但必须标清这 0.005 量的到底是什么——全文只用 §4.5 定下的那两句话。** A4–A6 与 A1 **共用同一个
检查点，只改采样参数**（见 4.5 节），所以它里面只有**采样随机性，不含训练随机性**：对这几个臂而言，
**0.005 是采样层噪声的上界**（若 k 其实没饱和，里面还掺着真实的 k 效应，纯采样噪声只会更小）。
而 A7–A11 全部是**重新训练**出来的臂，它们之上还叠着一层重训方差——同一份配置换一个随机种子重训会差
多少，**本项目未测量**（没有做多种子重复）；对这几个臂而言，**0.005 是总噪声的下界**，真实的显著性
门槛只会比它高，不会更低。两句话量的是两个不同的东西，不构成矛盾；本节比较的全是重训臂，所以以下每
一个倍数都按**总噪声下界**读。若还有算力，把 A1 或 A9 换一个种子重训一次就能给出真正的重训噪声——
这一步尚未做。（第 7.2 节沿用同一个 0.005 与同一对措辞。）

**开跑之前，我们据此做过一个预测，而结果把它推翻了。** 预测是这样的：A3 关掉整套对抗只值 0.034，
四个部件若把它均分，每个约 **0.008**，仅为噪声下界的 1.7 倍，所以这组实验大概只能看出"有没有某个
部件占压倒性主导"，分不开四个相近的贡献。这个预测写进了 `run_critic_ablation.py` 的文件头，
是在看到任何结果之前记下的。

它错在**前提**，不在算术。前提是"四个部件的效应可加，加起来等于 A3"。实测（5.7 节）单独关掉任一部件
的损失是 **0.072–0.107**，而整套关掉只损失 **0.045**——每一个单项都比整体大。可加分解这个前提不成立，
建立在它之上的功效推断自然也不成立。

按实测重新判断功效：观测到的效应量是 0.072–0.107，而这些重训臂的总噪声下界是 0.002–0.005，
两者差 **14 到 21 倍**。即便真实的重训噪声比这个下界高出数倍，这些效应依然是稳的。
所以"分辨不出"这个担心在**效应存在与否**这个层面上不成立。

**但有一条限制换了个位置，依然成立，而且更要紧**：四个部件之间的**精细排序不可信**。
四个臂的配对差挤在 0.072–0.107 之内，相邻两臂（A9 +0.073 与 A11 +0.072）只差 0.001、
远在噪声下界之内，A9 与 A10 也只差 0.010（约为总噪声下界的 2 倍）；考虑到重训噪声未被测量、真实门槛只会更高，
这个差距完全可能是噪声。本节能支持的结论是"**没有单一部件可以被去掉**"，
**不能**支持"哪个部件最重要"的排序。5.7 节给出各臂数字时，请按这个尺度读。

（它是关于 feature 通路的），只是它不是决定这四个数大小的主要因素。

### 5.8 与预期相反的一点：部件之和远大于整体

原计划是"把 0.034 拆成四份"。实测拆不出来：在同样的 scroll+swipe 12 格上，
**整套对抗全关（A3）只损失 0.045，而单独关掉任何一个部件损失 0.072–0.107**——

| 臂 | 拿掉的部件 | 配对差 |
|---|---|---|
| A8 | feature critic | +0.107 |
| A10 | waveform critic | +0.083 |
| A9 | set critic | +0.073 |
| A11 | feature_match | +0.072 |
| | **四者之和** | **0.334** |
| A3 | **四件全部拿掉** | **+0.045** |

四份之和 0.334 与整体的 0.045 **差着一个量级**。这不是舍入误差，也远超 0.005 的噪声量级。

**这里必须补一个限定，它决定了上面那个比值能被引用到什么程度。** A3 与 A8–A11 都是**独立的重训运行**
（A3 从它自己协议的那次训练里采样，见 4.4 节；A8–A11 各是一次新训练），每一个都带着一份重训方差，
而按 5.6 节，这份方差**从未被测量过**——0.005 对这些重训臂只是总噪声的下界，这里没有可靠的重训噪声
估计可用。所以能说的只有：即便把这项未知波动按最坏方向放大，0.334 与 0.045 之间仍差一个量级，
**"四个部件的效应不可加"这个定性结论成立**；而**具体倍数（0.334 / 0.045）建立在两个都不干净的数
之上，全文一律不引用**——包括 §7.2 在内，只说"差着一个量级"。

**换一个判据，这个结论更强而不是更弱。** 把同样 12 格改用 test EER（见 1.4 节，
文献常用的那个操作点）重算：A3 四件全关 +0.029，而单独拿掉一件是
A8 +0.074、A10 +0.061、A9 +0.056、A11 +0.056，四份之和 0.247 —— 是整体的 **8.4 倍**
（FAR 判据下是 7.4 倍）。四臂彼此的极差从 0.035 缩到 **0.018**，即四个部件在 EER 下更接近等价。
两个判据下的排序也完全相同（A8 > A10 > A9 ≈ A11）。所以「不可加」不是某一个判据的产物。

照实说，能给出的只有一个方向性解释而非结论：这四样东西不是可加的贡献项，
去掉其中一个会让剩下三个失衡，一个不平衡的对抗目标比完全没有对抗目标更有害。
按上文说明的功效边界，这批数据**能**支持"没有单一部件可以被去掉"：四个臂在共同的 12 格上
分别是 A8 = 0.682、A9 = 0.716、A10 = 0.706、A11 = 0.717，彼此的极差只有 **0.035**，
而它们对同格 A1 基准 0.789 的差距是 0.072–0.107，量级一致——**没有哪一个部件的缺席能被其余部件补上，
也没有哪一个显著突出**。

它**不能**支持任何关于四者相对权重的精细排序：极差 0.035 分摊到四个臂之间，相邻两臂
（如 A9 +0.073 与 A11 +0.072）只差 0.001，远在噪声下界之内；即便相隔最远的 A8 与 A11
也只差 0.035，而按 5.6 节，重训噪声从未测量、真实门槛只会比 0.005 更高。
"哪个部件贡献最大"这个问题，本节给不出可信答案，**也不需要它**——
"四件缺一不可"这个结论本身已经足够支撑发布版的设计。

## 6. 迁移表：用发布版出厂的检测器去打所有攻击

### 6.1 这张表回答的是另一个问题

主表（第 3 节的对比表与第 4 节的消融表）给每个攻击**各训一个检测器**：防守方见过这个攻击再来判它。迁移表反过来——不训任何新东西，直接搬出发布版**出厂自带的那 90 个已拟合检测器**，用它们各自在开发集上选好的 FRR=5%（拒真率 5%）阈值去判所有攻击的假事件。

实现在 `comparison/code/score_against_fixed_detector.py`（作者工作树里叫 `code/baselines/score_against_fixed_detector.py`，换算见开头那张路径对照表）：模型从 `direct100k_final/detector_models/` 读，阈值从各格 `thresholds.json` 的 `frr5` 字段读，两者都不重算；特征提取、归一化、前向都调用发布版当初用的同一套函数（`security_exp.formal_event_pad`），以免走成一条略有差别的流水线。全程纯推理。

所以这张表衡量的是**防御的泛化性**：针对攻击 A 训出的检测器遇到攻击 B 还剩多少能力——即发布版检测器的**盲区大小**。

| Diffusion-TS（轨迹臂） | 轨迹 | 30 | 0.763 | 0.750 |
| ghost-cursor | 轨迹 | 24 | 0.704 | 0.692 |
| pyclick | 轨迹 | 24 | 0.658 | 0.663 |

ghost-cursor 与 pyclick 是 24 格而非 30 格：这两个库在 keystroke（按键）上主动声明不适用（`declined`），该动作没有格子。

### 6.3 它绝对不能当攻击强度读

最直接的证据：TTS-GAN 在主表上是全场最弱的攻击，均值 **0.124**（30 格中仅 1 格达到 0.60）；这张表上它是 **0.877**，排第五。每个第三方 IMU 方法都发生同样的反转——CSDI 0.292 → 0.892，Diffusion-TS（IMU 臂）0.325 → 0.913，ImagenTime 0.683 → 0.924。

原因不复杂：这些出厂检测器是**在发布版的产物上训出来的**，学会的是"发布版生成的假 IMU 长什么样"。别的生成器的产物不属于它们已知的假样本分布，于是被判成真人放行。分数高说明的是"跟发布版**不一样**"，不是"**质量高**"。Control 组把真人窗口原样塞进假样本通道拿到 0.942 的上界，正印证这一点：越靠近 0.942 只意味着越"不像发布版"，而真人本来就最不像。

TTS-GAN 这一例就足以说明问题：只报迁移口径，会把一个平均挡下 87.6% 伪造事件的攻击写成第五强。这就是主表必须保持"每攻击各训一个检测器"口径、迁移表只作独立一节的理由。

### 6.4 发布版自身的 0.835 为什么两张表相同

发布版在迁移表上是 0.835，和它在主表 IMU 通道上的 0.835 是同一个数。这是构造上的必然：对发布版而言，"用该攻击训练出的检测器"和"出厂冻结的检测器"就是同一批模型、同一批阈值，两列按定义重合。不要把这一行读成"本方法在迁移意义下也很强"——它只是把主表数字原样搬来，为其他行提供刻度。

### 6.5 自检：打分器实现正确

用发布版检测器打发布版自己（`crossscore/_release_selfcheck.json`），30 格全部取到，逐格与 `reference_final.json` 已发表的值相比，**最大 |差| = 0.0000**，中位 FAR 0.840。打分器只要在模型加载、阈值读取或特征流水线上有任何偏差，这 30 格都不可能逐位复现。

### 6.6 消融臂不做交叉打分

迁移打分只对第三方基线做。消融臂（第 4、5 节的 A2–A11）用的本来就是本方法自己的生成器，只是去掉某个部件，对发布版检测器来说是"近亲"而非"没见过的东西"；交叉打分它们只能回答"检测器认不认得自家变体"，与这张表的目的无关。规则写在 `crossscore_queue.sh`（未发布，内部调度脚本）里，`abl_*` 前缀直接跳过。

照实说明：这条规则加入前，四个消融臂已跑出过交叉分数并留在磁盘上（IMU 通道，各 24 格：`abl_fewshot_nonadv` 0.838、`abl_krefs3` 0.840、`abl_noshot_adv` 0.833、`abl_krefs1` 0.830）。它们**不进表**，此处列出只为让人看到残留文件时知道来历；24 格也与表内 30 格不可直接比较。

### 6.7 已知局限

- **只报每个方法自己动过的通道。** 纯 IMU 方法没碰过轨迹通道，其"轨迹格"跑的其实是发布版原样的轨迹数据——Control、CSDI、Diffusion-TS（IMU 臂）、ImagenTime、TTS-GAN 五者的 `trajectory_xytime` 均值全部等于 **0.777**，即 §3 表中发布版轨迹的那一格（四位小数 0.7775，逐格完全一致）。表里因此只保留各方法覆盖的通道。
- **没有逐检测器、逐动作的迁移分解。** 现有汇总只到"方法 × 模态"的均值与中位一层，六个检测器之间、五个动作之间的差异在迁移口径下**未测量**。主表和消融表里"树模型是短板"那类结论不能直接搬过来。

## 7. 局限与可复现性

已知会削弱结论的地方全部列在这里，包括对我们自己不利的。凡是没测的都写"未测量"，不推断。

### 7.1 第三方基线采样用的是"早停那一刻"的模型，不是最优检查点

（§3.3 在介绍 ImagenTime 时只给一句结论"这个基线被略微低估了"；成因、逐动作差距、为什么没修，集中放在这里，两处不重复给。）

ImagenTime（Naiman 等，NeurIPS 2024，把时间序列变成图像再用扩散模型生成）由我们自己写的驱动脚本 `comparison/code/run_imagentime.py` 训练。原作者固定训 1000 个 epoch（一个 epoch = 把训练集完整过一遍），我们改成早停：每 25 个 epoch 抽一批样本和真实数据比 lag-1 自相关、逐通道离散度、窗口摘要的能量距离（energy distance），合成一个"gap"（越小越接近真实），连续 3 次没改善就停。

问题出在实现上：脚本只有**一个**检查点文件反复覆盖，收敛监视器里的 `monitor.best_step`（历史最优那一步）**只被打印，从不被恢复**。所以早停后采样用的是停止那一刻的权重，而不是历史上 gap 最小的那一版。实测差距（`comparison/notes/imagentime.md` 的 "Every deviation" 一节逐动作记着同一组数）：

| 动作 | 停在 | 停止点 gap | 最优检查点 | 最优 gap |
|---|---|---|---|---|
| tap | 574 | 0.370 | 499 | 0.361 |
| pinch | 399 | 0.399 | 324 | 0.373 |
| swipe | 374 | 0.421 | 299 | 0.352 |
| scroll | 449 | 0.427 | 374 | 0.334 |
| keystroke | 424 | 0.778 | 349 | 0.568 |

**必须明说：ImagenTime 的所有数字都被略微低估了。** 它是唯一进入我们同一量级的第三方方法（IMU 通道 30 格均值 0.683，第二名 Diffusion-TS 轨迹臂只有 0.460；发布版 0.835）。换成最优检查点它只会更强。keystroke 的差距尤其大（0.778 对 0.568），而 keystroke 恰好也是它逐动作 FAR 最低的一个（0.533）——方向一致，但**没有做控制实验**证明因果，只作提示。

为什么没修：最优权重已被后续 epoch 覆盖，磁盘上找不回来，唯一办法是整套重训（五个动作），这个成本没有付。监视器状态现在会写进检查点，重训不会再丢，但重训本身未做。

同类的预算问题还有一条：ImagenTime 用的是作者自己 `mujoco.yaml` 里那个更窄的 UNet（1440 万参数，对比默认的 1.517 亿）。这是作者提供的配置选项而非我们改模型，但同样意味着这个基线没有跑在最大配置上。

**一条曾经会自我复活的旧数字（已修，记录在此以免再被误引；本段提到的 `RESUME_BASELINES_CN.md`、`STATUS.md`、`status_daemon.sh` 都是内部运维文件，未发布）。** 项目笔记 `RESUME_BASELINES_CN.md` 与 `STATUS.md` 一度都写着"ImagenTime（300 epoch，作者是 1000，差距要写进论文）"。300 是**早停接入之前的计划值**，已被上表逐动作实测的停止 epoch（374–574）取代——实际训练比那个计划值多跑了一截，照抄 300 会低报这个基线。麻烦在于 `STATUS.md` 由 `status_daemon.sh` 每 5 分钟整份重写，手动删掉也会长回来，而就地修改运行中的 bash 脚本会破坏它的读取偏移。成稿时的处理是：先停掉守护进程，再改 `status_daemon.sh` 第 96 行的文案与 `RESUME_BASELINES_CN.md` 的对应句，然后重启守护——现在两处都写的是实测早停区间，`STATUS.md` 里已无"300 epoch"。ImagenTime 的 epoch 数以 `comparison/notes/imagentime.md` 与上表为准。

### 7.2 critic 消融能排除"单一部件主导"，但给不出部件排序——因为四份之和远大于整体

噪声水平用 A1、A5、A6 三个**本应给出相同结果**的臂测出（24 格均值 0.835 / 0.832 / 0.830，配对差 +0.004 与 +0.005），得到 **0.005**。按 §4.5 定下的口径，这个数只有两种读法，本节用后一种：对 A1、A4–A6 这类**共用同一个检查点、只改采样参数**的臂，**0.005 是采样层噪声的上界**；对 A7–A11 这类**重新训练**出来的臂，**0.005 是总噪声的下界**（重训方差从未测量，真实门槛只会更高）。本节比较的是重训臂，所以下面每一个倍数都是相对**总噪声下界**说的。

事前的担心是"四个部件的效应会小到测不出"：A3 的整体效应只有 +0.034（24 格口径），四份若均分每份约 0.008，仅噪声的 1.7 倍。**实测把这个担心推翻了，换成了一个更麻烦的问题。** 在同样的 scroll+swipe 12 格上，单独关掉一个部件的配对差是 A8 **+0.107**、A10 **+0.083**、A9 **+0.073**、A11 **+0.072**，是 0.005 噪声下界的 14–21 倍——单部件效应根本不小；而整套对抗全关（A3，同两动作口径）只有 **+0.045**。四份之和 0.334 与整体的 0.045 **差着一个量级**（具体倍数不可引用，理由见 §5.8：两个数都带着未测量的重训方差）。所以真正的限制**不是功效不足，是效应不满足可加性**：第 5 节对此只给了方向性解释（去掉一个部件会让剩下三个失衡，一个失衡的对抗目标比完全没有对抗目标更有害），不是结论。

由此，这组实验**能**支持的是"没有单一部件可以被去掉"：四个臂在共同的 12 格上分别是 A8 = 0.682、A9 = 0.716、A10 = 0.706、A11 = 0.717，彼此极差只有 0.035，而它们对同格 A1 基准 0.789 的差距是 0.072–0.107，量级一致——没有哪一个部件的缺席可以被其余部件补上，也没有哪一个显著突出。**不能**支持的是任何相对权重排序：相邻两臂（A9 +0.073 与 A11 +0.072）只差 0.001，相隔最远的 A8 与 A11 也只差 0.035，而重训噪声从未测量、真实门槛只会比 0.005 更高，"哪个部件贡献最大"这个问题本文给不出可信答案。这段限定已写进 `run_critic_ablation.py` 文件头，要求出表时和数字一起给。

### 7.3 对照判据 test EER 是较弱的协议，与主判据不可混引

`RESULTS_EER.md` 里那套 EER 是在**评测集上**定位等错误点得到的——阈值是看着评测分数挪出来的，属于对评测集的一次窥视。本文的主判据不这样做：FRR=5% 的阈值在开发集上定、冻结后才碰评测集（`test_threshold_selection_calls: 0`）。之所以仍然提供 EER，是因为行为生物识别文献多数这么报，不给就没法比。发布版自己的产物把同一个量命名为 `descriptive_test_eer`，就是在标注它只作描述之用。

两条具体限制：**(a)** 两张表的数字不可互相引用——同一批格子，发布版 IMU 在主判据下是 0.835、在 EER 下是 0.397，因为 FAR 上界 1.0 而 EER 上界 0.5；**(b)** 「≥0.60 的格子数」这一列只对主判据有意义，EER 口径下 0/90 格过线，那是尺度而非结论。可比的读法是相对真人对照的天花板（EER 0.447）：发布版 89%、ImagenTime 67%。

**未测量**：EER 一侧没有 bootstrap 区间。主判据一侧同样没有（见 2.3 节），两个操作点的不确定度都缺，表里相近的两个均值不要当作有显著差异来读。

### 7.4 A7–A11 只覆盖两个动作，因此只有 12 格

完整网格是 5 动作 × 3 模态 × 6 检测器 = 90 格。A2–A6 五个臂都覆盖 24 格（4 动作 × 惯性模态 × 6 检测器），但它们"重训了没有"并不相同：A4–A6 只改采样时传给采样器的参考条数，复用发布版的同一个检查点；A2/A3 是**换协议重训**的（README 原话 drawn from this protocol's own training run，见 §4.4 对这一混淆项的说明），只是沿用既有训练管线，没有动训练时的梯度与损失路径。真正的分界在这里：A7（梯度合并换成普通加权求和）和 A8–A11（关掉各个 critic / feature_match）**必须改训练时的梯度或损失路径并重新训练生成器**，受算力所限只做了 scroll 和 swipe，tap、pinch、keystroke 没做。所以这些臂都是 12 格：`abl_a7_weighted_sum` 0.734（≥0.60 有 9 格）、`abl_a8_no_feature` 0.682（8 格）、`abl_a9_no_set` 0.716（9 格）、`abl_a10_no_waveform` 0.706（9 格）、`abl_a11_no_feature_match` 0.717（9 格）。

原因是成本：GPU 空闲时实测 162 epoch/小时，一个臂全程约 21 小时（训练 4h + 采样 13h + 排格 4h）。

**对结论的限制**：这些臂的均值和 24 格的臂**不可直接比较**，因为动作构成不同（缺的 tap 和 pinch 恰好是发布版分数偏高的两个动作，IMU 通道上分别是 0.881 和 0.883）。表里"vs release"是逐格配对差，只有这一列跨臂可比。两个动作的结论能否外推到另外三个，**未验证**。

### 7.5 keystroke 的假 IMU 不经过扩散生成器

keystroke 的伪造惯性通道由一个解析式适配器写出（构建产物里记为 `diffusion_used: false`），不走扩散模型。所以**任何针对生成器的消融都碰不到 keystroke**，它按构造被排除在整张消融表外，这也是消融表分母是 24 而不是 30 的原因。关于生成器各部件的一切结论，适用范围都不含 keystroke。

### 7.6 k_refs 消融测的是参考编码器的泛化，不是"为该 k 值专门训练"

A4/A5/A6（k_refs = 1 / 3 / 8）**复用发布版的同一个检查点**，只在采样时改传给采样器的参考条数，而这些检查点是在各自协议自带的参考条数下训练的。所以这三个臂衡量的是参考编码器在训练之外的参考条数上泛化得如何，**不是**"用 k 条参考从头训练会得到什么"——后者未测量。该限定在 `ablation/notes/abl_krefs1.md`、`abl_krefs3.md`、`abl_krefs8.md` 的 "What this arm does not measure" 一节里逐份写明。

### 7.7 实验过程中发现并修掉的四个会静默毁结果的缺陷

写这一段不是自我批评，而是让读者知道**这几类失败模式已经被主动找过并堵上了**。它们的共同点是不报错、不告警，只是让结果悄悄变错。

1. **计划文件被整份重写，下游空等 12 小时。** `run_a7_weighted_sum.py` 按 `--actions` 把 `a7_plan.json`（未发布）整份重写，用 `--actions swipe` 重跑时把 scroll 的条目冲掉了；下游判断"训好了没有"的 `trained()` 读不到 scroll 的目标就永远返回 "no"。A7 早就训完，流水线仍空等了 12 小时。修法：`run_critic_ablation.py::merge_plan()` 按 `(动作, 臂)` 合并写入。
   *影响范围*：只影响调度，被冲掉的是计划文件不是训练产物，A7 的权重和样本都完好；**未影响任何进表数字**。*处置*：代价是 12 小时墙钟，无需重跑。

2. **检查点按修改时间挑，挑到了错误的族。** 原来用 `ls -t best_*.pt | head -1` 取"最新的"，这个通配同时匹配 `best_*` 和 `best_post_adv_*` 两族。发布版 scroll 用的是 `last.pt`，A7 却挑中了 `best_epoch0096`——A7 于是同时变了两件事，测的不再是它声称的那个变量。修法：`pick_ckpt()` 逐动作镜像发布版钉死的那一族。
   *影响范围*：A7 的 scroll 那 6 格（swipe 未受影响）。*处置*：**已重跑**——清掉 2908 条污染样本，按发布版钉死的检查点族重新采样、重新排格；本文与 `RESULTS.md` 表 2 里的 A7 数字（12 格 0.734、+0.054、9 格 ≥0.60）出自修复后那一轮，磁盘上的产物链时间递增可查：`train_scroll.log` 08-08 06:12 → 样本缓存 `a7_weighted_sum_cache` 12:36 → 格子目录 `final/abl_a7_weighted_sum` 13:48。

3. **ImagenTime 的收敛监视器状态不进检查点。** 最隐蔽的一条。scroll 的第一个实例在 449 早停并正常收尾；调度器随后又起了第二个实例，它从检查点续跑但监视器是全新的——同一个 epoch 449 被评了两次，**更差的那次 gap（0.550 对 0.427）成了新"最优"，耐心计数清零，早停再也不会触发**；再往下走一步就会覆盖已被用来建样本库的 `samples_scroll_imu.npy`。修了三处：监视器状态存进检查点并在续跑时恢复；`run_imagentime_all.sh` 加 PID 锁；`scheduler.sh` 启动前先查是否已在跑。
   *影响范围*：**覆盖是险些发生而未发生，现表里的 ImagenTime scroll 数字没有被污染，也不需要重采。** 证据：`imagentime/scroll/log_scroll.txt` 里 `saved (4000, 208, 6) to samples_scroll_imu.npy` **只出现一次**，写在第一个实例"early stop at epoch 449"那一行之后（文件时间 08-08 13:18），而建库产物 `bank_final_imagentime.pkl` 是 13:19——晚一分钟，读的正是这份；第二个实例被发现并终止时正跑到 epoch 470，从未走到采样那一步（它只把 `ckpt_scroll.pt` 推到了 13:43）。*处置*：代价仅是那段白跑的算力；§7.1 那张表里 scroll"停在 449 / gap 0.427"就是这次正常收尾的读数。

4. **`pgrep -fc ... || echo 0` 产生两行输出。** `pgrep -c` 无匹配时**已经打印了 0** 且退出码非零，`|| echo 0` 又追一行，结果是 `"0\n0"`。所有拿它做数值比较的地方都抛 `integer expression expected` 然后按"假"穿过去——即所有"有没有任务在跑"的判断全部失效。四个脚本都有这个写法：`scheduler.sh`、`status_daemon.sh`、`run_ablation_queue.sh`、`critic_pipeline.sh`。正确写法是 `n=$(pgrep -fc "$p" 2>/dev/null | head -1); n=${n:-0}`，四处已全部改成这一形式。
   *影响范围*：只影响调度判断，没有任何进表数字流经这条路径；但它是第 3 条那个重复实例得以被起起来的直接条件（`scheduler.sh` 正在这四个脚本之列）。*处置*：**未影响任何进表数字**，代价是重复起进程与空转的算力。

配套防御：所有"完成没有"的判据都改成从磁盘产物读而不是记账（`grid_job_done.py` 读 `completion.json`、`covered_modalities.py` 读 `release.json`、`released_generators.py` 读样本自带的 `metadata_json`），并配了回归测试（这两份测试在上游代码树里、不在本 `evaluation/` 目录内；快照时刻从磁盘数出：`tests/test_smoke.py` 39 个测试函数、`tests/smoke_end_to_end.sh` 16 项端到端检查，后者含 9 个模块导入检查与一条"故意喂坏数据看校验器会不会拒"的反向用例）。

### 7.8 可复现性：19 份从产物自动生成的说明

仓库里共 **19 份**可复现说明：`comparison/notes/` **9 份**（三个 Diffusion-TS 臂、CSDI、ImagenTime、TTS-GAN、pyclick、ghost-cursor，加真人对照 `control_genuine`）与 `ablation/notes/` **10 份**（A2–A11 十个消融臂；A1 就是发布版本身，没有单独的说明）。作者工作树里它们叫 `final/<name>/README.md`，换算见开头那张路径对照表。每份记录：哪些代码原样跑、**每一处偏离原作者实现的改动及其理由**、这个方法声明了哪些动作（**declined（拒绝报数）**的动作显式列出，例如 pyclick 和 ghost-cursor 都 declined keystroke，因此它们是 24 格）、以及结果表。

关键在于这些说明由 `comparison/code/write_baseline_readmes.py` 从构建产物生成——读 `release.json` 里的 `method_detail`、样本旁边的训练摘要、bundle 清单的逐动作替换计数——**不是凭记忆写的，因此不会和实际跑的东西漂移**。唯一的例外是 §3.2 记的那句 CSDI 五-shot 臂的硬编码文字，它不是从产物读出来的，靠人工维护。

成稿时这些说明已按终表重跑过一次，所以与终表一致：`comparison/notes/imagentime.md` 已是 30 格 / 0.683 / 20 格过线，`RESULTS.md` 表 2 的 A1–A11 十一行全部有数，`ablation/scores/ablation_cells.csv` 是 10 个臂 × 逐格共 180 行。

生成脚本本身在成稿时修掉了一处会误导读者的缺陷，一并记录：原来判断"这个臂用的是不是发布版那个检查点"只比对**检查点文件名**，而每个重训臂的 scroll 检查点也叫 `last.pt`，与发布版 scroll 的 `last.pt` 同名不同源——A7–A10 会被写成"与发布版共用检查点"，读者就会以为它们没重训。同时，缓存里的 `ablation.json` 由采样器每次调用整份重写，A7–A11 是逐动作采样的，于是该文件只留下最后一个动作（swipe），scroll 的溯源整条消失。现改为**从每条样本自带的 `metadata_json` 按动作读取、并比对 run 名**：样本级溯源不会被覆盖，run 名也能区分同名不同源的检查点。修复后 A7–A10 正确报告为"两个动作都来自本臂自己的重训"，A4–A6 仍正确报告为"与发布版同一检查点"。
