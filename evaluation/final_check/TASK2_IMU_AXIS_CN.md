# 任务 2：连续 IMU 轴 —— 数据分析与结论（更正）

> **更正**：我此前说"连续 IMU 做不了、数据不在"。用数据核实后，这个说法**错了**。连续 IMU **存在**，就在原始 HMOG 归档里，而且这条轴比触摸节律轴**更强**。下面全部用实测数字说明为什么、以及做它还差什么。

## 1. 逐事件数据集为什么没有连续 IMU（实测）

会话节律检测器 v1 只用了触摸节律，不是因为 IMU 不存在，而是因为**发布用的逐事件数据集把 IMU 切成了手势窗口**：

- `datasets/scroll/shards/*.npz` 的 `imu_flat` 是逐事件拼接，单个 scroll 事件只有 **9 帧 / 80 ms**——只覆盖手势本身。
- `data/processed/hmog_scroll.npz` 也是 `windows`（逐手势窗口，T=179 帧），无跨事件连续流。

所以**手势之间的 IMU 在这些数据集里=无**。v1 只能用触摸时间戳（`flat_system_time_ms`）重建节律。这是数据集形态的限制，不是原始数据的限制。

## 2. 原始 HMOG 有连续 IMU（实测）

原始归档在 `/home/mwang49/Human_agent/hmog_dataset.zip`（6.1 GB，逐用户 session）。每个 session 目录里有：

```
100669_session_1/Accelerometer.csv   5.8 MB   连续加速度
100669_session_1/Gyroscope.csv       6.4 MB   连续陀螺
100669_session_1/TouchEvent.csv      触摸事件
```

实测 session_1 的连续加速度：

| 量 | 值 |
|---|---|
| 样本数 | 76,855 |
| 时长 | 782 s |
| 采样率 | **98 Hz** |
| 覆盖 | **整段 session 连续**（非逐手势） |
| 幅值 | 中位 9.27、std 0.19 m/s²（握持手机的手部微动） |

**连续 IMU 完整存在**，覆盖整段阅读/输入/导航活动。

## 3. 手势之间的背景 IMU 是个强判别信号（实测，核心）

把每个 IMU 样本按"是否在触摸 ±200 ms 内"分成"手势期间/手势之间"：

| | 样本占比 | 背景运动 std |
|---|---|---|
| 手势期间 | 25% | 0.1343 |
| **手势之间** | **75%** | **0.2022** |

关键发现：

- **75% 的 IMU 在手势之间**——人握着手机的绝大部分时间不在做手势。
- 手势之间的背景运动 std（0.20）**比手势期间还高**——人在调整握姿、阅读、微动。
- 逐 2s 窗看手势之间的背景：378 个窗，运动 std 中位 **0.0825**、5% 分位 0.0486。
- **接近死寂（std<0.01）的真人窗占比 = 0.0%**。

**含义**：一个只在手势瞬间注入 IMU、手势之间沉默的机器，在这 75% 的时间里背景运动≈0——而**0% 的真人会这样**。这是一个**近乎完美的判别信号**（历史上 pressure 也是这种"近乎完美的 tell"）。所以连续 IMU 轴比触摸节律轴**更强**：节律轴可以靠复制人类间隔分布化解（见 EVALUATION），但死寂的空档骗不过去，除非真的填上连续背景运动。

## 4. 这条轴其实是我们方法**已经设计**要打的

ActReal 的注入器维持一条**连续 100 Hz 背景 IMU 流**（素材是缓存窗口的 padding 区——"手势前后仍在动的手"），动作之间不沉默。所以：

- 一个**朴素**自动化（只在手势注入、空档死寂）会被这条轴 100% 抓住。
- ActReal 的连续背景**正是**为了填这个死寂。**但这一点还没被这条轴测过。**

## 5. 那到底还差什么（为什么现在没直接跑出来）

不是数据不在，是要一条**真实的数据处理链 + 攻击侧的连续流**：

| 环节 | 状态 |
|---|---|
| 真人连续 IMU | ✅ 在原始归档（6.1 GB），需从 zip 逐 session 抽取 Accelerometer/Gyroscope，按触摸时间线对齐 |
| 真人背景特征 | ✅ 已验证可算（上面的 std/2s 窗占比就是） |
| **攻击侧连续背景流** | ⚠️ **这是唯一的真缺口**。ActReal 会注入连续背景，但要评测得有**真机 Agent 跑出来的连续 IMU 流**（或按注入模型合成）。现在没有真机 run，合成又有自证风险（用我们的背景模型生成、再用检测器测我们的背景模型） |
| session-IMU 检测器 | 待建：2s 窗的背景运动特征 → 同 FRR=5%/1% 操作点 |

## 6. 结论（诚实、完整）

- **不是"做不了"**——连续 IMU 数据存在（原始 HMOG，98 Hz，整段连续），而且手势之间的背景是个**比触摸节律更强**的判别轴（0% 真人窗死寂）。
- **现在没直接跑出数字**的原因有两个，都不是数据缺失：① 要写一条从 6.1 GB 原始 zip 抽连续 IMU、按触摸时间线对齐、切 2s 窗算背景特征的处理链（工程量，可做）；② 攻击侧要有真机 Agent 的连续 IMU 流才能公正评测，否则用我们自己的背景模型生成又测它就是自证。
- **建议**：这条轴留到有真机 run 之后做（真机才有真实的注入背景 + LLM 时延节律）。届时它大概率是最能区分的一轴，也是 ActReal 连续背景设计成败的直接检验。在此之前，把上面的真人背景分析（75%、std 0.20、0% 死寂）作为**动机证据**写进论文的 session-level 章节即可。
